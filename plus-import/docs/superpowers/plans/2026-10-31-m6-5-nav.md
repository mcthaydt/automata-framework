## Scope

In: `packages/nav` (`@mcthaydt/automata-nav`, private like `sectors`, since its consumers are private while D-1
stands):
- the `nav-graph` content schema;
- the pure functions `route`, `clear` and `nearestNode` on `dmath.hypot` and `sortedKeys`;
- the `Blocked` query, built from `sectors`' `segmentBlocked`;
- the `walk-to` command, the `nav-agent` component, the `nav-doors` resource with its `nav.door` command, and the
  `nav.arrived` and `nav.unreachable` events;
- recomputing a route only when a door changes;
- a four-engine golden, N-a and N-b.

Out:
- the `nav-click-to-walk` example (needs M6.4b);
- `reserveNodes` and `reachable`: these are the source's pursuit helpers, so they belong to `systems` (M6.7a), which
  takes them over;
- box obstacles: the source's `BOXES` are the game's level props, so a game passes them through its own `Blocked`.

## Interfaces

Consumed:

- `defineExtension` (`@mcthaydt/automata-runtime/extension`).

Produced (the spec's names):

```ts
export interface NavGraph { readonly nodes: Readonly<Record<string, Point>>; readonly edges: readonly (readonly [string, string, string?])[] }
export interface Blocked {
  /** Whether the plan segment a→b is blocked within `margin` (walls, tall steps, a game's boxes). */
  segment(a: Point, b: Point, margin: number): boolean
  /** Whether a door (an edge's third member) is open. */
  open(door: string): boolean
}
export function route(from: Point, to: Point, graph: NavGraph, blocked: Blocked, margin?: number): readonly Point[]
export function clear(a: Point, b: Point, blocked: Blocked, margin?: number): boolean
export function nearestNode(p: Point, graph: NavGraph, blocked: Blocked, margin?: number): string | undefined
export const navPlugin: PluginDef   // `walk-to` and `nav.door` commands, `nav-agent` component, `nav-doors` resource, `nav.arrived` and `nav.unreachable` events
export const navExtension: ExtensionDef<'nav'>
```

- The `walk-to` command is `{ entity, to: Point }`.
- The `nav-agent` component holds the speed (m/s), the target, the current leg and the route's door version. It
  moves the walker's `InSector` x and z, which is sectors' plan position (S4-D6), in the `gameplay` phase. Sectors'
  membership then runs in `cleanup`, the same step.
- **Where the route lives.** The route is stored in a `nav-routes` resource keyed by entity, because components hold
  only numbers. A route is recomputed when `nav-doors` changes (the door version), never per tick.
- **Unreachable.** `route` falls back to `[to]` the way the source does. The plugin emits `nav.unreachable` when that
  fallback leg is not `clear`, and does not walk.

## Decisions for the Owner's veto

- **N-D1:** `Blocked` carries the door state (`open(door)`) as well as the segment query, so the pure functions keep
  the spec's parameter list and the door record stays one resource.
- **N-D2:** `nav` moves sectors' `InSector` plan position (S4-D6) rather than a component of its own, so nav and
  sectors agree on where a walker is without a copy.
- **N-D3:** `reserveNodes` and `reachable` go to `systems` (M6.7a), their only user.
- **N-D4:** `nav` is private, like `sectors`.
