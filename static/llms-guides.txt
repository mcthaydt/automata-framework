# Automata Framework — Site Guides for Coding Agents

> Automata is a deterministic 2D game framework for the modern web and Ruken platform.
> Strict Core Laws: Koota ECS determinism, Effect outside sim, Zero Eval CSP, PixiJS 2D sub-tick alpha interpolation.

---

# The 5 Golden Rules for LLMs
1. Simulation is Pure and Deterministic: NEVER import Effect, browser DOM, or PixiJS inside simulation systems.
2. Effect Outside the Sim: Side effects (I/O, audio, network, saves) run in Effect outside the sim.
3. Zero Eval: Never use eval() or new Function(). Strict CSP compliance required.
4. Sub-tick alpha interpolation: Presentation interpolates positions between ticks: prev.x + (curr.x - prev.x) * alpha.
5. Single State Ownership: Only the sim mutates game entities; UI and presentation only observe truth.

# Overview & Vision

Automata is a TypeScript game framework for modern web browsers and Ruken, the reference gaming host.

Automata is designed for developers using coding agents: agents write code and tests; people direct the game and author its content. Start with a working example, make a bounded change, and review the result.

## License

> [!NOTE]
> Framework code is MIT licensed. Third-party dependencies and example artwork retain their own stated terms. See the repository license and asset provenance before redistributing assets.

## Ownership

Only simulation systems change gameplay state during a run. Input sends commands. PixiJS reads render deltas. Effect manages resources and side effects outside the simulation.

## Current starting point

Explore the 2D starter and focused examples before adding your own systems. The Last Light and FloorFifty are reference projects that informed the architecture.

## Packages

# Quick Start

## Play before setup

[Try the double-jump remix](/start#worked-change) in your browser. Jump, release, and press again before landing. Toggle the extra jump off to compare the original. The same page includes the prompt, source, and tests.

## Run the starter locally

Use Node 24.21.0 or newer and pnpm 10.34.6.

```sh
git clone https://github.com/mcthaydt/automata-framework.git
cd automata-framework
pnpm install --frozen-lockfile
pnpm --filter @af-examples/base-2d dev
```

Open the URL printed by Vite and play Emberwick. The starter is a working TypeScript browser game that you can edit directly or with a coding agent.

## Give your agent one idea

[Copy the double-jump task](/start#first-task). It adds one extra jump through a plugin, reuses the existing player input and movement definitions, and tests held input, landing, and snapshots. [Install agent skills](/docs/agent-setup) for the guided workflow when you set up your agent.

A configurable player start is also included as a smaller content exercise. Its helper uses parseRoom to validate the new room while keeping the source content unchanged.

## Check and play the result

```sh
pnpm --filter @af-examples/base-2d check
pnpm --filter @af-examples/base-2d build
```

Try the new behavior and the original controls yourself. Ask the agent to report the files changed, the checks it ran, and any browser or device behavior it has not verified.

## Choose your next change

[Choose a task prompt](/ai#task-prompts) for a collectible, dash, jump feedback, room content, saves, or release preparation. The [API reference](/cheatsheet) provides examples and current package entry points.

## License and scope

Framework code is MIT licensed; assets and third-party dependencies retain their own terms. Browser and mobile foundations are available. Networking and server packages remain planned. See [capabilities and licensing](/docs/capabilities).

# From Unity

Keep the habit of composing a game from small pieces. In Automata, separate the data that determines gameplay from the objects that draw it.

## Map familiar concepts

| Your starting point | Automata responsibility |
|---|---|
| GameObject and gameplay components | A simulation entity with data components; its PixiJS view is separate. |
| FixedUpdate gameplay rules | Synchronous systems running in fixed simulation ticks. |
| Update and visual feedback | Presentation and input outside the simulation; drawing can happen between ticks. |
| Scenes, prefabs and ScriptableObjects | Authored content plus explicit spawning and setup code. There is no scene or prefab importer. |
| Editor inspector tweaks | Edit typed content or tuning values and verify the result with tests and the playable example. |

## The habit to change

Avoid making each view object responsible for its own gameplay state. Send input as commands and let simulation systems own the resulting state.

## Your first small port

Start by moving P in Emberwick’s room content. Read room.test.ts, then follow player-move.system.ts and play-room.ts to see how content, rules and drawing connect.

[Open Emberwick’s source](/examples?demo=base-2d) and [try the worked change](/start#worked-change).

## Compatibility and scope

Unity APIs, packages, serialized scenes and editor tooling are not drop-in dependencies. Port one mechanic first rather than translating a whole project.

[Current capabilities](/docs/capabilities).

# From Godot

A Godot scene tree combines several responsibilities. In Automata, identify which parts describe gameplay state, which parts draw it, and which parts manage input or resources.

## Map familiar concepts

| Your starting point | Automata responsibility |
|---|---|
| Nodes and scenes | Entities and data for gameplay, with separate PixiJS containers or HTML/Svelte UI for presentation. |
| _physics_process gameplay logic | Fixed-tick simulation systems. |
| _process visual updates | Presentation outside the simulation, including drawing between ticks. |
| Signals | Explicit commands and events at ownership boundaries; do not assume a global signal replacement. |
| Resources and exported properties | Typed content and tuning data, validated by the project’s parsers and schemas. |

## The habit to change

Keep the scene graph as a presentation structure. Do not turn it into a second owner of gameplay state.

## Your first small port

Read the room content and its validation tests, then trace input through play-room.ts into the movement system. Rebuild one small scene interaction as a command and system.

[Open Emberwick’s source](/examples?demo=base-2d) and [try the worked change](/start#worked-change).

## Compatibility and scope

There is no .tscn, GDScript or resource converter. Preserve the behavior you need, then implement it using Automata’s current APIs.

[Current capabilities](/docs/capabilities).

# From web development

TypeScript, Vite and browser tools will be familiar. The new discipline is to give simulation time and gameplay state explicit owners rather than updating them from every UI callback.

## Map familiar concepts

| Your starting point | Automata responsibility |
|---|---|
| Application state | Gameplay state belongs to the simulation; menus and UI can still own their own UI state. |
| UI components and DOM | Svelte/HTML UI or PixiJS presentation. Simulation components are data, not UI components. |
| requestAnimationFrame | Drive drawing per frame; advance game rules through the fixed-step loop. |
| Click/key callbacks | Translate input into commands instead of mutating gameplay entities from the view. |
| fetch, timers and cleanup effects | Resource work outside the simulation, with Effect-managed lifetimes where the runtime owns it. |

## The habit to change

Keep Date, Math.random, network requests and DOM access out of simulation steps. Use the framework’s deterministic inputs, time and RNG where gameplay depends on them.

## Your first small port

Read loop.ts and loop.test.ts, then trace play-room.ts from input to sim.step and renderer.draw. Make the configurable-start change before adding a new mechanic.

[Open Emberwick’s source](/examples?demo=base-2d) and [try the worked change](/start#worked-change).

## Compatibility and scope

A game loop is not a component rerender loop. Browser and device performance still require measurement, even when the source looks like a familiar web application.

URL: /docs/sim-ecs

# ECS Simulation & Determinism

## Definitions

Use defineComponent for fields, defineSystem for a synchronous run function, and definePlugin to register components and systems. Systems query entities through SimContext and write through entity.set.

## Creation and ticks

Await createSim with a seed and plugins. Creation can initialize plugin engines asynchronously. Once created, sim.step(commands) advances one fixed tick synchronously. The default tick rate is 60 Hz.

## Repeatable runs

Keep I/O, wall-clock time, Math.random, DOM and Effect outside simulation steps. Use context RNG streams and the framework's deterministic math where required. Replay equivalence depends on matching code, content, initial state and commands; use the cross-engine checks for evidence.

## Snapshots and lifetime

Use sim.snapshot() to serialize state and sim.restore(bytes) to restore a compatible snapshot. Call sim.dispose() when the simulation is no longer needed.

# PixiJS 2D Presentation

## Renderer setup

Import @mcthaydt/automata-render-pixi/no-eval before initializing PixiJS. createPixiRenderer returns a factory that accepts the runtime render target and produces a scoped Effect.

WebGL2 is the default. WebGPU is opt-in. Test the renderer you plan to ship on the devices you support.

## Between ticks

Presentation reads render deltas instead of changing gameplay state. Interpolate between previous and current values when drawing between simulation ticks.

```ts
sprite.x = previous.x + (current.x - previous.x) * alpha
```

## Working examples

The renderer example demonstrates presentation in isolation. Emberwick adds a playable room. Use those sources for the complete boot and disposal flow.

# Effect Runtime & Concurrency

## Boot

runGame accepts a GameDefinition and returns a RuntimeHandle. It owns boot attempts, resources and shutdown. Use the runtime package types for the full definition.

## Resource ownership

Effect scopes manage resource lifetimes outside the simulation. Keep file and network access, loading, timers and persistent saves out of simulation systems.

## Failure and recovery

Boot failures are typed. Inspect the runtime example for its loading, retry and failure behavior. A typed boundary makes failure explicit; it does not guarantee a game cannot crash.

## Document: Zero-Eval CSP & Ruken Security (Core)
URL: /docs/security-csp
Description: Avoiding dynamic evaluation under the host policy.

# Zero-Eval CSP & Ruken Security

## Dynamic evaluation

Do not use eval or new Function in game code. Ruken does not permit unsafe-eval. Import the renderer's no-eval entry before initializing PixiJS.

## Policy scope

Avoiding dynamic evaluation is one part of CSP compatibility. Asset origins, connections, workers and other directives must also match the host policy. Test the built game under that actual policy.

## Trust boundaries

Keep credentials outside game bundles. Validate host messages at the integration boundary. Use the supported hosting API instead of inventing another handshake.

# Mobile UI Primitives

## Geometry

createGeometryOwner tracks the space available to game UI, including host geometry and viewport changes. Use its state instead of independent measurements in every component.

## Layout and controls

ScreenFrame, ActionBar, CornerControls and Dialog provide building blocks. Check their current Props definitions rather than guessing component inputs.

# FAQ

## Do I need to know how to code?

You should be willing to read and change TypeScript, or learn it alongside your agent. Automata makes ownership explicit, but it does not turn game development into a no-code workflow.

## Do I have to use AI?

No. The framework is ordinary source code that you can edit and test yourself. The guided workflow is designed for coding agents, with human review and creative control.

## Which skills should my agent have?

Install Superpowers and the official PixiJS v8 skill collection for the agent you are actually using. Then ask it to report the available skills and load the relevant guidance. These are requirements for the recommended AI workflow, not runtime dependencies of your game.

## Which coding agents can I use?

Use an agent that can read the checkout, edit files and run tests. Installation differs between Codex, Claude Code, Cursor and other tools; the agent setup guide links the current upstream instructions.

## Can I sell a game built with Automata?

The framework code is MIT licensed, which permits commercial use under the license terms without requiring publication of your game source. Keep required notices and check separate asset, dependency, extension and tool terms.

## Can I make the content myself?

Yes. Edit room data, art, rules and narrative directly. The worked example lets you choose a starting position while reusing the existing simulation and renderer. You can also edit any of the code yourself.

## Does it run in browsers and on phones?

Browser delivery and phone-first UI foundations are available, with keyboard and touch examples. Test your own game on the devices, orientations and browsers you intend to support.

## Is multiplayer ready?

Networking and server packages are planned. Deterministic state, snapshots and replays provide foundations for that work; they are not a complete multiplayer service.

## Does it support full 3D today?

The current public starting point is 2D. Further rendering and full 3D work are on the roadmap. Choose based on current capability status rather than planned features.

## Can I import an existing engine project?

There is no automatic Unity, Godot, Unreal or GameMaker project converter. The migration guides map familiar concepts and recommend rebuilding one small mechanic first.

## How does it help a game grow beyond a prototype?

Explicit state ownership, separate systems and packages, and repeatable tests help keep changes bounded as the project grows. They do not promise a particular player count or performance level; measure your own game.

## What is Ruken?

Ruken is the reference gaming host integrated by the framework. The starter can also run standalone in a browser; see hosting guidance when adding platform services.

## How do I get my game into the showcase?

Use the community showcase submission link. Include a public playable URL, your creator name, a short description, the Automata version and screenshots you have permission to share. Submissions are reviewed before publication.

# AI workflow
URL: /ai

## Project context
- AGENTS.md: Project rules, architecture, and required checks. Read applicable instructions in the directories you will edit.
- package.json: Available scripts, tool versions, dependencies, and package exports. Read both the workspace and target package manifests.
- games/emberwick/src/base-sim.ts: Simulation creation, room content, command envelopes, and starting entities.
- games/emberwick/src/sim/: Working component, command, event, resource, system, and plugin definitions.
- The closest focused example: Use the one-file example for the integration being changed (examples/core, render, shapes, textures, audio), or content/hot-reload or ui/primitives.
- The nearest tests and public types: Actual accepted inputs, failure behavior, cleanup requirements, and exported names. Prefer these over a guessed API.

## Architectural boundaries
### Simulation owns gameplay state

Send commands from input and UI. Systems apply gameplay changes during fixed ticks. Initial scene setup may spawn entities before stepping; presentation observes the results.

### Keep ticks repeatable

No I/O, wall clocks, Math.random, DOM, or Effect in simulation systems. Use ctx.rng, deterministic math, stable traversal, and the same code, content, seed, and command stream when comparing runs.

### Effect owns work outside the sim

Use Effect for loading, hosting, saves, timers, and resource lifetimes. Keep simulation steps synchronous and close scopes, simulations, subscriptions, and render resources with their owner.

### Use the renderer boundary

Import the renderer no-eval entry before initializing PixiJS. Draw from render deltas, interpolate previous and current values, and handle a full resync after restore. Test the actual host content security policy.

### Honor host capabilities

Use Hosting and the Ruken SDK. Wait for readiness, check granted capabilities, validate saved data, and report save failures. A denied hosted capability must not silently fall back to device storage.

### Keep shared contracts canonical

Extend the component, schema, service, or package that owns a behavior. Keep content, snapshot, replay, and host contracts in their existing owners. Check the exact package entry point before using an export.

## Add a collectible

Add a collectible without letting its sprite become the source of truth.
API: /cheatsheet#defineSystem

```text
Add a collectible to Emberwick that can be collected once when the player overlaps it.
Read the room, player components, goal system, plugin, and movement tests first.
Keep collectible state and collection rules in the sim. Emit a registered event
for presentation to consume; a sprite callback must not award the collectible.
Test overlap, non-overlap, and repeated ticks at the same location.
Use a fixed room and seed. Verify that only one collection event is emitted.
Register all new definitions, run the focused tests and example checks,
and explain how to play and inspect the result.
```

## Add a dash

Carry a new action from keyboard and touch through a validated command.
API: /cheatsheet#defineCommand

```text
Add a dash action to the existing movement flow, with keyboard and touch input.
Read the input adapters, command schema, player-input system, movement system,
and plugin first. Reuse the current command envelope and sequence convention.
Input requests the action; the sim owns dash availability, duration, and movement.
Test accepted and invalid payloads, press versus hold, release or cancellation,
and attempts to dash while unavailable. Inspect StepResult.rejected for failures.
Keep keyboard and touch behavior equivalent and preserve existing movement tests.
Run focused tests and the example checks; list the controls for manual testing.
```

## Make jumps feel good

Make an event visible without changing the simulation from the renderer.
API: /cheatsheet#createPixiRenderer

```text
Add a short visual response when the player's existing jump event is emitted.
Read the event, renderer wiring, and nearest presentation tests before editing.
Keep the effect outside the sim and preserve the gameplay command stream and state.
Use the current PixiJS v8 APIs and the no-eval entry. Handle the first frame,
entity removal, restore resync, restart, and disposal without leaking views.
Respect reduced motion where the effect introduces nonessential movement.
```

## Author a room

Validate authored data and keep generated outputs reproducible.
API: /cheatsheet#defineContentSchema

```text
Add a validated content field for a game rule using the closest content example.
Read the current schema, TOML, compiler configuration, and consuming system first.
```

## Save progress

Persist progress through the host and explain failure states to the player.
API: /cheatsheet#Hosting

```text
Add a versioned progress save through the existing Hosting service.
Read examples/core/core-saves.ts, the runtime settings or save boundary, and tests.
Reuse the live session, wait for readiness, and check the saves capability.
Validate decoded payloads with Zod before applying any gameplay state.
Test missing, valid, malformed, incompatible, denied, and failed save/load cases.
Preserve stored data when loading fails. Keep I/O outside simulation systems.
Do not silently switch a denied hosted save to localStorage or device storage.
Distinguish a local update from remote persistence; inspect save status or flush.
Run relevant tests and report which hosted or standalone paths were verified.
```

## Review and verify
- Play the acceptance case yourself. Check the changed behavior and a nearby action that should still work.
- Review the diff: gameplay state has one owner, exports exist at the imported entry point, and generated data comes from its source.
- Read test assertions, including invalid input, failure, restart, and cleanup paths relevant to the change.
- Ask for the exact commands and results. Separate focused unit checks, a production build, browser behavior, host integration, and physical-device checks.
- For deterministic changes, compare the same seed, content, initial state, and commands. Investigate the first divergence before changing a golden hash.
- For mobile UI, check keyboard and touch, rotation, compact height, focus, and actions above the on-screen keyboard.

## Simulation
Import: @mcthaydt/automata-sim
URL: /cheatsheet#simulation
Source: https://github.com/mcthaydt/automata-framework/blob/main/packages/sim/src/index.ts

Define gameplay state and advance it with synchronous fixed ticks. Use instance methods on the Sim returned by createSim.

```ts
import { createSim, defineComponent, definePlugin, defineSystem } from '@mcthaydt/automata-sim'

const Counter = defineComponent('counter', { value: 'u32' })
const count = defineSystem({
  name: 'counter.advance',
  phase: 'gameplay',
  run(ctx) {
    for (const entity of ctx.query(Counter)) {
      entity.set(Counter, { value: entity.get(Counter).value + 1 })
    }
  },
})
const plugin = definePlugin({
  name: 'counter', components: [Counter], systems: [count],
})
const sim = await createSim({ seed: 1, plugins: [plugin] })
try {
  sim.spawn([Counter]) // Initial setup, before stepping.
  for (let tick = 0; tick < 60; tick++) sim.step([])
  const [entity] = sim.query(Counter)
  if (entity.get(Counter).value !== 60) throw new Error('Expected 60 ticks')
} finally {
  sim.dispose()
}
```

### createSim

Creates an isolated simulation and awaits plugin engine initialization. Once created, stepping is synchronous.

```ts
createSim(options: SimOptions): Promise<Sim>
```
Returns: Promise<Sim>
- options.seed (number): Seed for repeatable random streams. Use the same seed when reproducing a run.
- options.plugins (readonly PluginDef[]): Definitions to register, including required dependencies.
- options.tickHz (number): Optional integer from 1 to 1000. Defaults to 60 fixed ticks per second.
- options.content (unknown): Optional canonical JSON content, copied, frozen, and hashed at creation.
- Always await creation and dispose the sim when its owner closes. Duplicate definitions or invalid ordering reject creation.
- Replay equivalence requires matching code, content, initial state, tick rate, and commands as well as the seed.

### defineComponent

Declares per-entity fields. Read with entity.get and write with entity.set so changes appear in render deltas.

```ts
defineComponent<S extends FieldSchema>(id: string, fields: S, opts?: { render?: boolean }): ComponentDef<S>
```
Returns: ComponentDef<S>
- id (string): Stable lowercase ID with dot or dash separators, used in snapshots and render rows.
- fields (FieldSchema): Field names mapped to f32, f64, i32, u32, bool, entity, or string.
- opts.render (boolean): Optional; defaults to true. Set false for simulation-only data such as input buffers.
- Numbers default to 0, booleans to false, and strings to empty. Writes validate field types and ranges.
- Do not mutate the object returned by entity.get. Use entity.set with the fields you want to change.

### defineCommand

Defines a validated input payload. Register it in a plugin and read accepted commands through ctx.commands.of(definition).

```ts
defineCommand<Z extends z.ZodType>(id: string, schema: Z): CommandDef<Z>
```
Returns: CommandDef<Z>
- id (string): Command type in the input envelope.
- schema (z.ZodType): Zod schema that validates payloads before systems receive them.
- Keyboard, touch, and UI callbacks enqueue commands. Gameplay changes happen when a system consumes them.

### defineEvent

Defines an event emitted with ctx.emit and returned in StepResult.events. Register it in the owning plugin.

```ts
defineEvent<Z extends z.ZodType>(id: string, schema: Z): EventDef<Z>
```
Returns: EventDef<Z>
- id (string): Stable event ID, such as player.jumped.
- schema (z.ZodType): Zod schema for the emitted payload.
- React with audio and interface effects outside the sim.

### defineSystem

Declares synchronous gameplay behavior. Query matching entities through the context and write their components explicitly.

```ts
defineSystem(spec: { name: string; phase: Phase; run: (ctx: SimContext) => void; before?: readonly string[]; after?: readonly string[] }): SystemDef
```
Returns: SystemDef
- spec.name (string): Unique stable system name; also identifies its RNG stream.
- spec.phase (Phase): input, prePhysics, physics, postPhysics, gameplay, or cleanup, in that order.
- spec.run ((ctx: SimContext) => void): One synchronous tick. ctx.dt is the fixed step in seconds; ctx.rng is this system's stream.
- spec.before / spec.after (readonly string[]): Optional ordering constraints by system name. Invalid schedules fail at creation.
- Keep I/O, browser APIs, wall clocks, Math.random, and Effect outside run.
- A thrown system faults the sim. Restore a valid snapshot or recreate it before continuing.

### definePlugin

Registers a coherent set of definitions and optional engine state. Each sim owns its own plugin state.

```ts
definePlugin(spec: { name: string; components?: readonly ComponentDef[]; systems?: readonly SystemDef[]; dependsOn?: readonly string[]; commands?: readonly CommandDef[]; events?: readonly EventDef[]; resources?: readonly ResourceDef[]; state?: (setup: PluginStateSetup) => Promise<PluginState>; config?: unknown }): PluginDef
```
Returns: PluginDef
- spec.name (string): Unique plugin ID.
- spec.components / systems / commands / events / resources (readonly definition[]): Definitions this plugin owns. Omitted lists are empty.
- spec.dependsOn (readonly string[]): Names of required plugins.
- spec.config (unknown): Optional canonical JSON settings included in the schema hash, such as gravity.
- Optional state setup creates an engine with snapshot, prepareRestore, and dispose. Ordinary gameplay plugins usually need only definitions and systems.

### defineResource

Defines shared per-sim state such as round score. Systems access it with ctx.resource(definition).

```ts
defineResource<Z extends z.ZodType>(id: string, schema: Z, init: () => z.input<Z>): ResourceDef<Z>
```
Returns: ResourceDef<Z>
- id (string): Stable resource ID.
- schema (z.ZodType): Validates initial and restored values.
- init (() => z.input<Z>): Creates an independent initial value for each sim.
- Register the resource in its plugin. Keep gameplay updates in systems.

### step

Advances one fixed tick and returns the resulting tick, events, render delta, and rejected commands.
Instance method on Sim.

```ts
sim.step(commands: readonly Command[]): StepResult
```
Returns: StepResult
- commands (readonly Command[]): Envelopes contain tick, source, seq, type, and payload. tick is sim.tick before the call; source is a u8 player slot and seq is a u32 counter.
- Rejections report bad-header, unknown-command, wrong-tick, duplicate-seq, or invalid-payload. Inspect result.rejected when input seems ignored.
- Accepted commands are ordered by source and sequence. Keep sequence numbers distinct for a source within a tick.
- Presentation consumes the result and draws with a sub-tick alpha. Do not step gameplay from a second render loop.

### spawn

Creates an entity during initial scene setup and returns its stable ID.
Instance method on Sim.

```ts
sim.spawn(parts: readonly SpawnPart[]): number
```
Returns: number
- parts (readonly SpawnPart[]): A component definition or [definition, initial fields] tuple for each registered component.
- During gameplay, request spawns through commands and call ctx.spawn from a system. ctx.spawn takes parts as separate arguments.

### snapshot

Serializes canonical state, including resources, RNG, and plugin state.
Instance method on Sim.

```ts
sim.snapshot(): Uint8Array
```
Returns: Uint8Array

- A snapshot is state, not a persistent save service. Store bytes outside the sim with matching code and content.

### restore

Replaces live state with a compatible snapshot. Invalid data throws and leaves current state unchanged.
Instance method on Sim.

```ts
sim.restore(bytes: Uint8Array): void
```
Returns: void
- bytes (Uint8Array): Snapshot bytes for compatible definitions and content.
- Catch SnapshotFormatError and SnapshotMismatchError at the application boundary. Preserve saved bytes when loading fails.
- The next step emits a full render resync; let presentation rebuild its views.

### hash

Returns the current snapshot's XXH64 hash as 16 hexadecimal digits for equivalent-run comparisons.
Instance method on Sim.

```ts
sim.hash(): string
```
Returns: string

- Use describeSnapshot and the first differing tick to investigate divergence; a hash alone does not explain it.

### describeSnapshot

Decodes a readable snapshot without changing live state. Omit bytes to inspect current state.
Instance method on Sim.

```ts
sim.describeSnapshot(bytes?: Uint8Array): SnapshotView
```
Returns: SnapshotView
- bytes (Uint8Array): Optional snapshot. Header checks run; this does not replace full restore validation.


### dispose

Releases the world and plugin engines. Use in test teardown, runtime cleanup, and failed startup paths.
Instance method on Sim.

```ts
sim.dispose(): void
```
Returns: void

- Idempotent. Later state operations throw SimDisposedError.

### createRng

Creates a seeded stream with next(), nextU32(), int(n), and state(). Systems normally use ctx.rng.

```ts
createRng(seed: number): Rng
```
Returns: Rng
- seed (number): Seed for a standalone stream.
- rng.int(n) returns an integer from 0 inclusive to n exclusive. n must be a positive integer no greater than 2^32.

## Snapshots and replays
Import: @mcthaydt/automata-sim/replay
URL: /cheatsheet#replays
Source: https://github.com/mcthaydt/automata-framework/blob/main/packages/sim/src/replay/index.ts

Record accepted commands with checkpoints, encode a run, and verify it against matching plugins and content. Import replays through this simulation subpath.

```ts
import { createSim } from '@mcthaydt/automata-sim'
import { createRecorder, createReplayStepper, encodeReplay, decodeReplay } from '@mcthaydt/automata-sim/replay'

const sim = await createSim({ seed: 7, plugins: [] })
try {
  const recorder = createRecorder(sim, { checkEvery: 10 })
  for (let tick = 0; tick < 60; tick++) recorder.step([])
  const replay = decodeReplay(encodeReplay(recorder.finish()))
  const playback = await createReplayStepper(replay, { plugins: [] })
  try {
    const result = playback.run()
    if (!result.ok) throw new Error('Replay diverged at tick ' + result.failed?.tick)
  } finally {
    playback.dispose()
  }
} finally {
  sim.dispose()
}
```

### createRecorder

Captures the starting snapshot and records accepted commands while advancing through recorder.step.

```ts
createRecorder(sim: Sim, options?: RecorderOptions): Recorder
```
Returns: Recorder
- sim (Sim): Live simulation to record. Only the recorder may step it during recording.
- options.checkEvery (number): Optional positive checkpoint interval. Defaults to 60 ticks.
- options.reference ({ snapshotEvery: number }): Optional golden-run mode: per-tick hashes and periodic snapshots.
- finish() records the final hash and closes the recorder. Stepping the sim separately invalidates the recording.

### createReplayStepper

Creates a fresh sim from the starting snapshot and feeds recorded commands. run() stops at the first failed check.

```ts
createReplayStepper(replay: Replay, setup: ReplayStepSetup): Promise<ReplayStepper>
```
Returns: Promise<ReplayStepper>
- replay (Replay): Decoded or freshly recorded run.
- setup.plugins (readonly PluginDef[]): Matching plugin definitions.
- setup.content (unknown): Matching simulation content if originally supplied.
- Inspect result.ok, checks, and failed. Dispose the stepper when finished.
- Snapshot or header mismatches can reject creation before playback begins.

### encodeReplay

Encodes a recorded run to canonical, uncompressed bytes.

```ts
encodeReplay(replay: Replay): Uint8Array
```
Returns: Uint8Array
- replay (Replay): Run from recorder.finish().
- For compressed .replay files, use packReplay with a compression adapter.

### decodeReplay

Validates and decodes uncompressed bytes. Malformed data throws ReplayFormatError.

```ts
decodeReplay(bytes: Uint8Array): Replay
```
Returns: Replay
- bytes (Uint8Array): Output from encodeReplay. Compressed files need unpackReplay.

## PixiJS presentation
Import: @mcthaydt/automata-render-pixi
URL: /cheatsheet#presentation
Source: https://github.com/mcthaydt/automata-framework/blob/main/packages/render-pixi/src/index.ts

Draw render deltas without changing gameplay state. WebGL2 is the default; WebGPU is opt-in. Import no-eval before initializing PixiJS.

```ts
import '@mcthaydt/automata-render-pixi/no-eval'
import { createPixiRenderer, type EntityView } from '@mcthaydt/automata-render-pixi'
import { Graphics } from 'pixi.js'

// Expects a registered, renderable component named position with x/y fields.
export const renderer = createPixiRenderer({
  logicalWidth: 320, logicalHeight: 192,
  entityViews: {
    position: () => {
      const dot = new Graphics().circle(0, 0, 4).fill(0xffc857)
      const view: EntityView = {
        container: dot,
        update(current, previous, alpha = 1) {
          const now = current.position as { x: number; y: number }
          const before = (previous?.position ?? now) as { x: number; y: number }
          dot.position.set(
            before.x + (now.x - before.x) * alpha,
            before.y + (now.y - before.y) * alpha,
          )
        },
      }
      return view
    },
  },
})
```

### createPixiRenderer

Returns a GameDefinition renderer factory. The runtime supplies the host element, geometry owner, and assets.

```ts
createPixiRenderer(options?: PixiRendererOptions): (target: RenderTarget) => Effect.Effect<PixiRenderer, RendererUnavailable, Scope.Scope>
```
Returns: Scoped renderer factory
- options.logicalWidth / logicalHeight (number): Logical game dimensions for letterboxing.
- options.preference ('webgl' | 'webgpu'): Defaults to webgl (WebGL2). Opt-in WebGPU falls back to WebGL2 if initialization fails.
- options.entityViews (EntityViewResolver): Factory, or component-ID map of factories, creating one view per entity.
- options.setup ((stage: PixiStage) => void): Optional stage setup, such as filters.
- View updates receive current fields, previous fields when available, and interpolation alpha. Handle the first frame with no previous values.
- Keep simulation and rendering units consistent. Emberwick player positions use subpixels.

### RenderDeltaConsumer

Maps stable entity IDs to views. apply(delta) handles additions, changes, removals, and full resync.

## Hosting
Import: @mcthaydt/automata-host
URL: /cheatsheet#hosting
Source: https://github.com/mcthaydt/automata-framework/blob/main/packages/host/src/index.ts

Use Hosting for readiness, capabilities, saves, lifecycle, and platform actions. The Ruken SDK owns the host protocol.

```ts
import { makeHosting } from '@mcthaydt/automata-host'
import { Effect } from 'effect'

export const saveProgress = Effect.scoped(Effect.gen(function* () {
  const hosting = yield* makeHosting({
    gameId: 'my-game', wants: ['saves'], pauseBehavior: 'pause',
  })
  yield* hosting.ready
  if (!hosting.granted.has('saves')) {
    return yield* Effect.fail(new Error('Saves unavailable in this session'))
  }
  yield* hosting.saves.set('progress-v1', JSON.stringify({ version: 1, room: 'room-1' }))
  return yield* hosting.saves.flush
}))
// Run at the application boundary; handle the returned status or error.
// In a runtime screen, reuse yield* Hosting instead of creating a session.
```

- options.gameId (string): Must match ship.config.ts and ruken.toml.

- options.pauseBehavior ('pause' | 'continue'): Lifetime pause policy matching the manifest.
- seams (HostingSeams): Optional injected SDK environment for testing.

- config.runtime (Omit<Manifest['runtime'], 'allow_eval'>): Renderer, orientation, inputs, and pause policy. Ship sets allow_eval to false.
- config.network / content (ShipConfig): Declared connections, languages, rating, and descriptors.
- For the starter, run pnpm --filter @af-examples/base-2d build, then prepare-ruken. Preparation does not upload or activate a game.
- automata-ship publish uses RUKEN_API and RUKEN_TOKEN and delegates validation and upload to Ruken. Supply credentials in the environment, never browser code.
