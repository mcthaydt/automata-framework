# The paid desktop and mobile apps: spec

Stage 2 of the apps area. It argues from the [audit](2026-11-08-apps-audit.md) (PR #511, `3c7991df`) and the Owner's
words. The [plan](2026-11-08-apps-plan.md) builds it. The [plan audit](2026-11-08-apps-plan-audit.md) (#527:
5 high, 7 medium, 3 low) is applied here and in the plan. The 2026-11-09 update (iPad first, Apple Pencil, Publish and
the agent loop on an iPad, and the seven paid features) is applied here and in the plan; its evidence is the
[iPad gap list](2026-11-09-ipad-end-to-end-gaps.md).

## 1. What done looks like

**On an iPad, with nothing else.** The iPad is the primary device for making a game (the Owner, 2026-11-09 01:53), and
Claude Code is the primary surface: "the editors are just so we can modify things by hand if we need to" (01:58). So
done is this, with no computer anywhere:

1. The person makes a game in the Automata app and puts it on GitHub, or gets one Claude already made.
2. They ask Claude Code, in the Claude app, for the game they have in mind. Claude works on `claude/…` branches and
   opens pull requests; the game's own check runs on each one (section 9.4).
3. Each change waits on the Review page. The person plays it on the iPad, then says yes or no, or turns on "Use
   changes without asking".
4. They fix what they want by hand in the editors, with the Apple Pencil as a first-class tool (section 10.4) or a
   finger. The app keeps the game on GitHub both ways, so Claude sees the hand edits.
5. They press Publish: the app makes the zip, then puts the game on itch.io through the game's own release workflow
   (section 10.5). The game is online.

**On a computer**, the same app has nothing else to install, plays and publishes with the computer's own tools, uploads
to itch.io in one press, makes downloads for Mac, Windows and Linux, signs the Mac one with the person's own Apple
account, and says from the menu bar when Claude's change is waiting (section 10.6).

A person buys each app once: $39.99 on a computer, $19.99 on a phone or tablet, two separate purchases (the Owner,
01:50). In a later stage, the downloaded app (not the browser) lets a coding agent work in the open editors over MCP:
on a computer through the app's sidecar, on a phone over the same Wi-Fi while the app is open (section 11). Claude Code
on an iPad runs in the cloud, so it reaches the game through GitHub, never through MCP.

Every editor stays free on the web. All of this is MIT code in this repository except deployment: signing,
provisioning, store listings and the release pipelines, which live in a private repository.

## 3. What the web keeps and what the download adds

The web (the site's try-it page and the free `automata editor` command) serves the full page: every editor, in 2D and
3D games. The 3D editors join the public page the day Pixi 3D is public, as the shared-editors plan (#509 S4, S10)
already says.

The web also keeps GitHub sign-in and sync (#528, #536, through GitHub's REST API and a sign-in function on the site),
the in-page player (`kit/player`), and the Review page: Review reads and merges pull requests through the same REST API,
which allows a web page, and plays a change with the in-page player. The Owner's rule (2026-11-09 01:46) is that an app
never sells a limit of the free web, so none of these is held back.

The download adds only setup it takes away and what a device can do only as an app:
- on a computer: one install with Node inside, kept up to date; Play and Publish with no terminal; one-button itch.io
  upload with butler inside; downloads for Mac, Windows and Linux with no Rust; Mac signing with the person's own Apple
  account; a menu bar notice; double-click to open (section 10.6);
- on a phone or tablet: the app itself, playing games with no computer and full screen; the game as a real folder in
  the Files app; Publish from the device; real vibration on an iPhone; Apple Pencil double-tap and squeeze; a home
  screen widget (section 10.7);
- later, MCP access to the editors (section 11).

No editor, button or file format is gated. Nothing in the open code checks a licence key (audit section 5).

## 4. Where the code lives

```
apps/editor/                      the app (private package @automata/editor-app, MIT, not published)
  package.json  vite.config.ts  index.html
  src/
    app/          main.ts: picks the platform's ports and boots the full suite page
    features/
      desktop/    the sidecar's client: start, token, address, stop (desktop only)
      app-store/  the ProjectStore over the app's own folder (phones)
      player/     Play inside the app: the game compile and the play view
      sync/       GitHub: sign-in, the git engine, pull and push, merges
      review/     the Review port: waiting changes, use, close, undo
      publish/    the zip from the in-app compile, itch.io by tag (phone) or by butler (computer)
      native/     the page side of the native plugin: Pencil actions, haptics, the widget's count
      desktop-extras/  the game shells, Mac signing, the menu bar notice, opened files
      agent/      (later stage) the page side of MCP: tool calls to suite commands
    shared/       the Tauri bridge (the only files that import @tauri-apps/*), app origins
    entries/
  sidecar/        the Node program the desktop app runs: serveEditor plus the app's routes
  src-tauri/      Rust: windows, the sidecar's life, the play scheme, secrets; later the phone MCP server
    src/  tests/
    plugins/automata-native/  Swift (ios/) and Kotlin (android/): Pencil, haptics, audio session, the widgets
  tests/          unit/<feature>/, browser/, e2e/, fixtures/
```

`apps/` joins `pnpm-workspace.yaml` and `pnpm boundaries`. The app is a target's adapter in law 4's sense: only
`apps/editor/src/shared/tauri/` imports `@tauri-apps/*` (AGENTS.md "Host authority"). `packages/editor` never learns
Tauri exists; it gains optional ports (section 6) that the app fills.

Package names are read from one module, `apps/editor/src/shared/framework-packages.ts`, never written out elsewhere in
the app, so the `@automataframework` rename (audit A5, site plan #510) is one edit. This spec writes today's
`@automata/*` names.

A private repository, `mcthaydt/automata-apps-deploy`, holds only signing, provisioning, store metadata and release
workflows, and builds a pinned commit of this repository named in its `af.ref` (one full commit, as Plus did with
`core.ref`). It is the Owner's to create (section 14).

`TRADEMARK.md` at the root: a fork may ship the code under another name and icon, never as "Automata" in a store.

## 5. One page on five platforms

The app's window loads the app's own build of the full suite page (`tauri://localhost` on macOS, iOS and Linux;
`http://tauri.localhost` on Windows and Android). The page is the same suite the web serves, booted by
`apps/editor/src/app/main.ts` with the app's ports instead of the browser's.

| | Computer | Phone or tablet |
| --- | --- | --- |
| Files | `createHttpStore` against the sidecar on 127.0.0.1, with its token | `createAppStore` over the app's folder (Tauri file system plugin) |
| Editor list policy | The sidecar's (as `automata editor` today) | The same policy module, run in the page |
| Watch | The sidecar's change stream, `GET /api/watch` (server-sent events) | The store's own writes and every pull |
| Play | The game's own Vite, started by the sidecar, in a second app window | The in-app player (section 7), full screen |
| Publish | `vite build` and the zip, by the sidecar; ends with "Show the file"; itch.io with the butler it carries | The zip from the in-app compile, then itch.io through the game's release workflow (section 10.5) |
| Git | isomorphic-git, over Tauri's file system and HTTP plugins | The same |

**Origins are literal strings, per platform.** A custom scheme's origin is `"null"` to `new URL(...).origin` (the WHATWG
rule for non-special schemes), so `apps/editor/src/shared/app-origins.ts` holds them as strings and they are compared as
strings, never built through `URL`:

| | Page | Game (the play scheme, section 7) |
| --- | --- | --- |
| macOS, iOS, Linux | `tauri://localhost` | `automata-game://localhost` |
| Windows, Android | `http://tauri.localhost` | `http://automata-game.localhost` |

The window-message handlers that listen to a framed game (`extensions/editors/src/features/schematic/watch-bridge.ts`,
the solver client) accept the **game's** origin for the platform, and still check the source (AGENTS.md). The sidecar's
CORS reply echoes the page's literal.

The sidecar refuses cross-origin writes today (`serve-editor.ts:239`). It gains an `appOrigins` option: a request from
exactly those origins with the right token is served; any other origin is refused as now.

## 6. Seams in the editors (packages/editor)

Three optional ports, each "a missing optional port is the feature off" (`suite-ports.ts`):

1. **`SuiteHost`**: what the page asks of whatever holds it.
   ```ts
   interface SuiteHost {
     play(game: PlayRequest): void          // the web: window.open, as today
     showPublished?(path: string): void     // the app: open the zip's folder
     readonly publishes: boolean            // false on a phone: Publish says why instead
   }
   ```
   The v2 header's Play (`SuiteHeader.svelte:163`, today an `<a href={playUrl} target="_blank">`) becomes a button that
calls `host.play`, with the word "Play" beside its icon (an icon alone beside a worded "Publish" fails the drunk grandma
test, plan audit L3). The browser host opens the game in a new tab, as the link does today (A2).
2. **`ProjectStore.watch`**, implemented by the HTTP store and the app store. The HTTP store reads `GET /api/watch` with
   `fetch` and a streamed body, so the token travels in `Authorization: Bearer` as on every other route; an
   `EventSource` cannot send that header (plan audit M2). When a file under an
   open document changes: no unsaved change, the document reloads; an unsaved change, the existing conflict dialog
   opens (A6).
3. **`SuiteCommands`**: one command layer behind the page. Every action a button takes and a later MCP tool needs is a
   plain function: `listContent`, `readContent`, `writeContent` (through the editor's own write path, with checks and
   Undo), `openEditor`, `runChecks`, `play`, `publish`. The header's buttons call it. No command reaches into a
   component's state. MCP (section 11) needs nothing else from the page.

And two optional ports for sync and Review, `sync?: SyncStatus` and `review?: ReviewPort` (sections 8, 9), which the
app and the signed-in web page both fill. Without them the page has no Review row and no sync line.

Two more for the iPad (2026-11-09):
4. **`SuiteCommands.pencil(action: PencilAction)`**, with `PencilAction` one of `'eraser' | 'previous' | 'palette' | 'none'`
   (iPadOS's preferred actions, already mapped). The open editor handles it if it has tools; the others ignore it. The
   web never calls it (Safari does not report double-tap); the app's native plugin does.
5. **`publish?: PublishPort`**: the destinations a Publish offers on this host (`zip`, `itch`, `itch-by-github`) and the
   run of each. Without it, Publish is today's download of the zip.

## 7. Play on a phone with no computer

The Owner asked (21:28) whether a phone needs a computer as a bridge, the way Expo does. **No.** Expo needs one because
Metro bundles the JavaScript on the computer. The Automata app carries the bundler's job inside itself:

1. **A prebuilt runtime.** The app ships, already built, every package and browser subpath the games it promises
   import. The list is not written by hand: `runtime-manifest.ts` is generated from the 2D and 3D templates' and
   Emberwick's `package.json` dependencies and every browser subpath export those packages name, and a test fails when
   any of their imports does not resolve against it. Today that is `@automata/framework` (with its `theme.css`),
   `@automata/sim` and `/hash`, `@automata/content`'s browser entries (`/level-2d`, `/palette`, `/controls`, ...),
   `@automata/feel` and `/stage`, `@automata/audio-synth` and `/stage`, `@automata/3d`, `/sim` and `/level` (a 3D game
   reaches Pixi 3D only through these, and they carry `@pixi/3d` once it is public), `pixi.js`, `zod` and
   `@fontsource/pixelify-sans` (Emberwick's font; it is small, so it is carried rather than leaving Emberwick out).
   It is built with the `automata-web` resolve condition the templates set, and with the framework's Svelte screens
   already compiled. Its versions are the app's.
2. **The game's code, compiled on the phone.** A worker strips TypeScript with sucrase (as the site's playground does,
   `site/src/features/playground/compile.ts`), file by file, and rewrites imports to an import map onto the runtime.
3. **The game's content, compiled on the phone.** The content compiler's core (`compileTree`) is already pure. It is
   split from the Effect and `node:fs` code into plain modules (`compile-tree.ts`, `source-tree.ts`), together with the
   option checks that need no disk and the text of the `virtual:automata/content` module (built today in the Vite
   plugin, `automata-content.ts:72`), so the page runs it without Effect and law 5 holds with no ADR change. Its options come from the game's `src/content.config.ts`, a
   plain module the template now writes and `vite.config.ts` imports, so the computer and the phone compile the same
   way.
4. **The Vite features a game uses**, and only these: the plugins `svelte()` and `automataContent()` (every game has
   both: the framework's screens are Svelte components; the player accepts them and needs neither, because the runtime's
   screens come compiled); the `automata-web` resolve condition (any other condition, such as Emberwick's
   `automata-ruken`, is read as `automata-web` in the player, because the app is the host); `virtual:automata/content`;
   `import.meta.glob` with `{ eager: true, query: '?url' }` (the templates' music and pictures); CSS imports (injected as
   a style); `?url` on a file; `import.meta.env.DEV` (true); `__AUTOMATA_DEBUG__` (false); `import.meta.hot`
   (undefined: the templates guard on it). Checked: `template-project.ts:118,127,132`, `template-game.ts:182,235`,
   `template-3d-game.ts:149`, `template-level.ts:118`, `games/emberwick/`.
5. **Its own origin.** The compiled game is written to `.automata/play/` in the game folder and served by a Rust
   handler on its own scheme (`automata-game://localhost`, or `http://automata-game.localhost` on Windows and Android:
   section 5's table), a different origin from the editor page, with no Tauri
   capability, so the game cannot reach the app's native bridge (A7, Apple 4.7.2).

What plays only on a computer, said in words before Play is pressed, never after a blank screen:
- a game that imports a package the app does not carry: "This game uses three.js, which the phone app can't run. Play
  it on a computer.";
- a game made with a newer framework than the app carries: "This game needs a newer app. Update Automata to play it.";
- the game's own `.svelte` files in `src/`, or a `vite.config.ts` plugin other than `svelte()` and `automataContent()`:
  "This game uses <file>, which the phone app can't run. Play it on a computer." (the templates and Emberwick have
  none; `games/base-3d` has six and plays only on a computer);
- a game whose content options turn on `paraglide` (it writes its message files to disk): the same sentence, naming
  `content.config.ts`, until a later task compiles messages in the page.

Every game the templates make, 2D and 3D, and Emberwick play in the player (a test proves each, section 15).

**The same game as the computer's build.** The in-app compile uses sucrase where Vite uses esbuild, and an import map
where Vite bundles, so law 3 is checked, not assumed: for each template's game and Emberwick, a fixed seed and a fixed
input script give the same content hash and the same sim hash in the player as in `vite build`'s output, in Chromium,
WebKit and Firefox. A mismatch is a bug in the player, never a re-recorded hash. A zip that Publish makes on a phone
(section 10.5) is this compile, so it plays the same game too.

The Tuner's game pane on a phone shows the player, as it shows the game's Vite page on a computer.

## 8. GitHub sync

As the audit's section 7, with these decisions:

- **Engine.** isomorphic-git in the page on all five platforms, its `fs` over Tauri's file system plugin and its
  `http` over Tauri's HTTP plugin (allowed hosts: `github.com`, `api.github.com`). It writes a real `.git` that the git
  command and Claude Code read. The version is the newest release at least 14 days old when the build starts
  (`renovate.json`'s `minimumReleaseAge`); 1.44.11 (2026-11-05) is too new today.
- **Sign-in.** A GitHub App named "Automata", device flow, no client secret in the code. Permissions: Contents (read
  and write), Metadata (read), Pull requests (read and write), **Checks (read) and Commit statuses (read)** (added here:
  the Review page shows whether a change broke a check, which the audit's list could not read), and, for the iPad
  (2026-11-09): **Workflows (write)**, because a new game's first push carries `.github/workflows/check.yml` and
  `release.yml` and GitHub refuses a workflow file without it; **Actions (read)**, to follow the release run that puts
  the game on itch.io; **Secrets (write)**, to keep the person's itch.io key as the repository's `BUTLER_API_KEY`. The
  install page says why each is asked for, in one line each. Tokens live in the
  system keychain through Rust commands `secret_get`, `secret_set` and `secret_delete`. A platform with no keychain
  makes sign-in fail and say so; a token never goes to a plain file (AGENTS.md "never quietly falls back to device
  storage").
- **Which repositories.** A GitHub App's token reaches only the repositories the app is installed on. After the code
  step, the app opens the install page: "Choose which games Automata may sync". A game whose repository is not in the
  list says "Automata can't reach this game on GitHub yet." with a button "Let Automata see this game", which opens the same page.
- **A new game on GitHub.** The first version opens `github.com/new?name=<game>&visibility=private` and waits: "Make
  an empty repository on GitHub, then come back." It then pushes. (Administration permission to create it would ask
  for far more than sync needs.)
- **When.** Pull on open, on coming to the front and every 60 s while open, with a conditional request on the branch
  first (a 304 does not count against the rate limit). Push 10 s after the last save, one commit per batch: "Edited in
  Automata: Feel, Levels (Start)".
- **Conflicts.** The audit's eight rules, in order: git's three-way merge; TOML and JSON merged by key, arrays of
  tables by their id; then the person chooses per file ("Keep mine", "Keep GitHub's", "Keep both"); generated files
  made again from their source; pictures and sounds chosen whole; changed-here-deleted-there asks; never a force-push;
  offline commits wait.
- **Generated files.** A level's TOML changed on GitHub is made again from the merged `.af2d.json`. The status line
  says: "Claude edited content/levels/start.toml, but the app rebuilds that file from your level. Claude's edit is
  kept on GitHub, not in the game." (Taking such an edit into the level is not in this spec.)
- **The game's `AGENTS.md`.** `create-game` writes one: the files an agent may edit, that level TOML is generated from
  `.af2d.json`, and "work on a branch named `claude/…` and open a pull request; the person says yes in the app".
  `.automata/` is in the game's `.gitignore`.

## 9. The Review page

Built new; the stack deleted the old desk. As the audit's section 7, with these decisions:

### 9.1 Where and what

The editors v2 spec leaves Review out on purpose ("no 'Waiting for you' group, no Review row",
`2026-11-08-editors-v2-spec.md:51-53`), so this area creates the group, as drawn in the v2 mockup. It shows only when the
`review` port exists. Its Review row with the number of waiting changes at its end. The
page lists one card per open pull request whose branch starts with `claude/` or whose author is not the person:

- the title, the editors it touches ("Feel, Levels (Start)") and who made it;
- **Play it**, **Use this change**, **Not this one** (48 px buttons; on a phone they stack);
- a failed check: "This change broke a check: Feel", the three buttons still there;
- "See what changed": the diff, one file at a time, added lines and removed lines, text only (pictures say "A picture
  changed").

Empty: "Nothing waiting for you".

### 9.2 The three buttons

- **Play it** writes the branch's files into `.automata/review/<branch>/` from git's objects (no second checkout of the
  working tree) and plays that folder: on a computer the sidecar starts a second Vite there, its `node_modules` linked
  to the game's; on a phone the player compiles it. The person's game is not touched.
- **Use this change** merges on GitHub (`PUT /repos/{o}/{r}/pulls/{n}/merge`) and pulls. If GitHub says it cannot
  merge, the app merges locally with section 8's rules and pushes the merge commit to `main`; GitHub marks the pull
  request merged when its commits reach `main`. An overlap the rules cannot settle opens the conflict dialog.
- **Not this one** closes the pull request. The notice: "Closed. The change is still on GitHub."

### 9.3 Use changes without asking

A switch at the top of the page, one per game, off at first, stored in `.automata/app.json` (not synced). On, every
pull uses each waiting change whose checks passed, as "Use this change" would. It stops and leaves the card when a check
failed or an overlap needs the person. Each change it uses shows "Claude's change is in: Feel, Levels (Start). Undo"
for 8 s, and joins "Used without asking" on the page (the last 10, each with Undo). Undo is a new commit that puts back
the merged files as they were on the merge's first parent: "Undo Claude's change: <title>". Never a force-push.

### 9.4 Claude's changes on an iPad

Claude Code on an iPad runs in the cloud and reaches the game only through GitHub, so this page is the iPad's whole
loop with Claude (gap G1). Two things make it safe to say yes from a tablet:

- **A check on every change.** A new game gets `.github/workflows/check.yml` beside `release.yml`: on every pull request
  it runs `pnpm check` and `automata check-player`, which runs the in-page player's compile on the branch and fails with
  the player's own refusal ("This game uses three, which the phone app can't run."). Review reads that check like any
  other (G2, G3).
- **Before "Use this change".** The page compiles the exported branch with the player before it shows the card. A
  change the device can't play says so on the card, above the buttons: "This change won't play on your iPad: it uses
  three." "Play it" is then off; "Use this change" and "Not this one" stay, because a person may still want the change
  on a computer. The game's `AGENTS.md` and the agent skill state the player's limits, so Claude rarely writes one.

From the app to Claude: the game menu has "Work on this with Claude". It copies the repository's name ("Copied
mcthaydt/lantern-run. Paste it into Claude Code.") and opens the Claude app (G7).

## 10. The two apps

### 10.1 Desktop (macOS, Windows, Linux)

- Tauri runs `apps/editor/sidecar` with the Node it carries (`externalBin`, about 30 MB packed). The sidecar runs
  `-tools`' `editorCommand` (not `serveEditor` alone: the command prints the address and wires the game runner and
  Publish) with `--port 0 --token <random> --app-origin <origin>`; Rust reads the "This computer:" line and gives the page the address
  and token through a Rust command.
- First open of a game without `node_modules`: the sidecar runs npm. This needs the framework on a registry a stranger
  can reach, so it waits for the first npm release and the `@automataframework` rename (A5, section 14); until then the
  desktop app opens only games whose packages are already installed. With the release, the page shows "Getting your game ready…
  This takes a minute the first time."
- Home: "Make a new game", "Open a game on this computer", "Get a game from GitHub".
- Play opens a second window titled "<Game>: playing" (`on_new_window`, A2). Publish ends with "Show the file" (A9).
- Quitting sends SIGTERM to the sidecar in `RunEvent::Exit` and waits up to 5 s, so it stops the game's Vite (A10).
- Updates: Tauri's updater. The endpoint and public key come from the build's environment; unset, the updater is off
  (a from-source build has none). Settings: "Updates need the key from your receipt email." with a Purchase key field.
  The key only fetches updates; the app never stops working without one.
- The header (`SuiteHeader.svelte`) shows the whole editor and game names on a phone-sized window, and the Levels toolbar scrolls inside its declared
  region (A18).

### 10.2 Phone and tablet (iOS, Android), iPad first

The iPad is the device this app is designed and proved on first; a phone is the same app in the compact layout.

- The game lives in the app's folder: `Documents/Games/<game>/` on iOS, visible in the Files app under "On My iPad ›
  Automata" (`UIFileSharingEnabled`, `LSSupportsOpeningDocumentsInPlace`), so it can be AirDropped or opened in another
  app; the app's files folder on Android. Not iCloud Drive: iCloud downloads and evicts files on its own schedule, which
  breaks a git folder (G19). GitHub is the copy kept elsewhere.
- The iPad app allows Split View, Slide Over, Stage Manager and every orientation (`UIRequiresFullScreen` false). The
  layout follows the window, as the v2 editors do: at a third of the screen (320 to 507 pt) it is the compact layout
  (G16). It opens full screen from the home screen with no browser bars.
- Pictures for Add tiles come from the file picker (Photos and Files) or are dropped onto the dialog from another app in
  Split View (G14).
- Home: "Make a new game" and "Get a game from GitHub". A new game is made with no Node: the template folders are
  embedded at build time in a generated module (a test keeps it equal to the folders), and the file list comes from
  `create-game`'s existing `templateFilesOf(options)` (`template.ts:22`). The 3D template is offered when the runtime
  carries `@automata/3d`, the phone's own form of `three-d-gate.ts`.
- Play: the player, full screen, with "Back to editing" (48 px) at the top.
- Publish: section 10.5.

### 10.3 Nothing is lost

The Owner's rule (2026-11-08 21:35): progress persists. A phone may end a background app without warning, and a
computer may be shut down with the app open, so:

- every Save writes through to the game's files at once (the app store keeps nothing only in memory), and the page
  flushes pending autosaves on `visibilitychange` (hidden) and `pagehide`;
- a commit made but not yet pushed is pushed on the next open, with no second commit;
- the GitHub sign-in, "Use changes without asking" and the last 10 changes it used survive a restart;
- the app reopens the last game it had open.

Section 15's journey closes the app and opens it again.

### 10.4 Apple Pencil, first-class

The rule everywhere: **the Pencil edits, fingers move the view.** The gesture kit already does this
(`recognizer.ts`: once a Pencil is seen, a finger is a palm or only pans and zooms), and Levels and Levels 3D use it.
This spec makes it hold in every editor (gaps G8 to G13):

- **Every surface that takes a drag goes through the kit** (`attachGestures`): the Sequence and Studio timelines join
  Levels, Levels 3D and the Studio's stage. A resting palm never drags a key. A test fails the build if an editor adds
  its own `pointerdown` drag outside the kit; dialogs, popups and the reorder list, which are kit widgets, are the only
  others.
- **Per surface:** Levels and Levels 3D as today (draw, place, select; two fingers undo, three redo; the loupe and the
  nudge pad). The Studio in Pose: the Pencil moves only handles and a Pencil drag on empty stage does nothing; fingers
  turn the camera. The timelines: the Pencil drags keys, fingers scroll the timeline.
- **Every other editor** (Tiles, Characters, Document, Audio, Feel, Schematic, Writer) is buttons, fields and taps, where
  a Pencil tap is a click. One test per editor taps its main control with a Pencil and sees the result.
- **Hover** (iPads with Pencil hover): Levels shows the brush or eraser's cells under the hovering Pencil, as it does
  for a mouse; Levels 3D shows the snapped point and the loupe. Hover never edits.
- **Double-tap and squeeze** (native, section 10.7): they follow the person's own Pencil setting in iPadOS
  (`UIPencilInteraction.preferredTapAction` and `preferredSqueezeAction`). "Switch between current tool and eraser":
  Levels swaps Brush and Eraser, Levels 3D swaps the current tool and Select. "Switch between current tool and last
  used": the last tool. "Show colour palette" and "Show ink attributes": the editor's tool picker opens at the Pencil.
  "Off": nothing. An editor with no tools does nothing. On a Pencil Pro, a squeeze shows the tool picker beside the
  Pencil's tip, and snapping to the grid in Levels 3D gives the Pencil's own small tap
  (`UICanvasFeedbackGenerator`).
- **Handwriting** (Scribble) works in every text field, Writer's lines first: the kit sets `touch-action: none` only on
  drag surfaces, never on a field. Proved on a real iPad.
- **In a game being played**, a Pencil counts as touch: it shows the on-screen controls as a finger does (today it
  counts as a mouse and hides them, `hosting-web.ts:179`, G12).
- **Not used:** pressure, tilt and barrel roll. Tiles and walls are whole cells, so there is nothing for them to vary.

### 10.5 Publish from a phone or tablet

Publish on a phone or tablet follows the Owner's order (2026-11-08): the zip first, then where it goes (G20 to G24).

1. **The zip.** "Make the zip" runs the player's compile (section 7) and adds the runtime files it plays on, so the zip
   is a whole web game: an `index.html`, the game's modules, the runtime and the assets, nothing fetched from
   elsewhere. It is saved to `Documents/Published/<game>-<version>.zip` (Files: "On My iPad › Automata › Published"),
   with "Share" (the share sheet: AirDrop, Mail, another app) and "Show the file" (opens Files there).
2. **itch.io.** "Put it on itch.io" uses the release workflow every game already has (`template-ci/release.yml`: on a
   `v*` tag it checks, builds with the game's own Vite and pushes with butler), so the game on itch.io is the
   computer's build, made on GitHub's runners. The first time, the app asks two things, one per screen:
   - "Which itch.io page is this game?" (`<user>/<game>`, with "Make a page on itch.io" opening `itch.io/game/new`,
     and the one line "Tick 'This file will be played in the browser' there once.");
   - "Paste your itch.io key" with "Get a key on itch.io" (opens `itch.io/user/settings/api-keys`). The app seals the
     key with the repository's public key and keeps it as the `BUTLER_API_KEY` secret. It is never kept on the device.
   Then, each time: "Which version is this? 0.2.0" (the next patch, editable), Publish. The app writes the version into
   `package.json`, commits "Version 0.2.0", tags `v0.2.0`, pushes both, and follows the run: "Putting it on itch.io… This
   takes about two minutes." It ends with "Your game is on itch.io." and "Open it". A failed run says which step, in
   words ("itch.io didn't take it: the check failed. See what went wrong" opens the run). A tag that already exists
   says "Version 0.2.0 is already out. Choose a newer one."
3. **Offline:** "Make the zip" works; "Put it on itch.io" says "Publishing needs the internet." and keeps nothing half
   done.

A game not on GitHub can make the zip; "Put it on itch.io" says "Put your game on GitHub first, so it can build
there." with that button.

### 10.6 What the computer app adds (the Owner, 2026-11-09 01:52)

- **itch.io in one press.** The app carries butler (pinned with its checksum, as `release.yml` pins it) and asks once
  for the person's itch.io key, kept in the system keychain (`secret_set`). Publish's destinations on a computer are
  "Save the zip", "itch.io" (butler from the app, no tag needed) and, when the game is on GitHub, "itch.io through
  GitHub" (section 10.5's route). The same Publish dialog serves both apps through one `PublishPort`.
- **Downloads for Mac, Windows and Linux with no Rust.** The deploy pipeline builds a game shell once per system: a
  Tauri program that shows a web game from its own resources folder. The app copies the shell for each system, puts the
  game's web build in its resources, sets the name and icon, and zips it: "Download for Mac", "for Windows", "for
  Linux". No compiler runs on the person's computer.
- **Mac downloads that open without a warning.** With the person's own Apple Developer account (their $99 a year), the
  app signs and notarizes the Mac download. It uses the `apple-codesign` crate, which signs and talks to Apple's notary
  service from any system with an App Store Connect API key, so no Xcode is needed. Settings, "Sign Mac downloads":
  the Developer ID certificate (`.p12` and its password) and the API key (issuer, key id, `.p8`), all in the keychain.
  Without them the download is unsigned, and the dialog says "Macs will warn before opening this. Add your Apple
  account in Settings to stop that." Windows' own warning stays (a Windows code-signing certificate is not in this
  spec).
- **A menu bar (or tray) icon.** With "Keep Automata in the menu bar" on (on by default), closing the window leaves the
  icon. Every 5 minutes it asks GitHub, with a conditional request, how many of Claude's changes wait for each recent
  game. A new one shows a notice, "Claude's change is waiting: <title>", and the icon shows the count. Clicking either
  opens Review on that change.
- **Double-click to open.** A new game has `<game>.automata` at its root (one line: the game's name; `create-game`
  writes it and the app adds it to an older game when it opens it). The app registers the `.automata` type, so a
  double-click opens the game; dropping a game folder on the app's icon opens it too. A plain folder still opens in
  Finder or Explorer: neither lets an app own folders. Opened games join the system's recent documents, so the Dock
  menu (Mac) and the jump list (Windows) list them, and Home lists them first.

### 10.7 What the phone and tablet app adds (the Owner, 2026-11-09 01:52)

- **Real vibration on an iPhone.** The app fills the game's haptics port (`game-definition.ts`: "the device's haptics,
  in place of the browser's") with the phone's own haptics through `Hosting`, as any host capability. Android gets the
  same. An iPad has no vibration motor: the port is absent, and Feel says "This iPad can't vibrate. Try it on a phone."
  (G18).
- **Apple Pencil double-tap and squeeze**: section 10.4.
- **A home screen widget** (iPhone and iPad, small and medium; Android, one size): the last game's name and "2 changes
  from Claude are waiting", or "Nothing waiting". A tap opens the app on Review. The app writes the count to the app
  group's shared folder each time it syncs; the widget also asks GitHub itself about every 30 minutes, with the token
  from the shared keychain group, so the count is right when the app has not been opened. No server: AF hosts nothing.
- **Sound that plays.** The app sets the playback audio session, so Audio and a played game make sound with the silent
  switch on, as a game app should (G17).

**Native code is MIT and lives here**, in one Tauri plugin, `apps/editor/src-tauri/plugins/automata-native/` (Swift in
`ios/`, Kotlin in `android/`, the widget targets beside it). The private deploy repository holds only signing,
provisioning, store listings and release workflows (section 4), as before.

## 11. MCP access to the editors (a later stage)

Starts after the apps' build audit and fixes. Designed now so the apps leave room (section 6's command layer).

### 11.1 Tools

`list_content`, `read_content`, `write_content` (through `SuiteCommands.writeContent`: the editor's checks, Undo, and
the open editor shows it), `open_editor`, `run_checks`, `play`, and on a computer `publish`. Shaped like the editors,
not like raw files: an agent can already read files.

### 11.2 One bridge

The page owns the tools; a server is only a door. The server receives a call, hands `{ id, tool, args }` to the page,
and returns the page's answer. The page side (`features/agent/`) is the same on every platform. Each call the agent
makes shows on the status line ("Claude changed Feel. Undo"), and Undo takes it back.

### 11.3 Computer

The app's sidecar (`apps/editor/sidecar`, never the free `automata editor` command) adds a Streamable HTTP endpoint at
`/mcp` on 127.0.0.1, guarded by its own token, and `automata-mcp`, a stdio command that forwards to the running app (not
a second server). Both use `@modelcontextprotocol/sdk` at the version AF already pins for `@automata/pipelines`
(1.32.1, `docs/versions.md`). The pipelines' gate tools stay in their own server; the app's tools are the editors'. Settings: "Let Claude use the editors" and "Paste this into Claude Code:" with the command and a Copy
button.

### 11.4 Phone: local Wi-Fi only

- The server is Rust in the app, listening on the local network only while the app is on screen. It stops when the app
  leaves the screen and starts when it returns.
- Pairing: a 128-bit token, shown as one command to paste on the computer, with Copy and Share buttons. A new token
  each time the switch is turned on.
- iOS asks for local network access the first time (`NSLocalNetworkUsageDescription`: "Lets Claude on your computer
  work in your game over your Wi-Fi."). Android needs no foreground service, because nothing runs in the background.
- **No relay, now or later** (the Owner, 21:29). A person who wants to reach it from elsewhere sets up their own port
  forwarding or tunnel; the app and the docs say so: "To reach it from somewhere else, set up your own port forwarding
  or tunnel. Automata doesn't run one."
- The words beside the switch: "Claude can work in your game while this app is open on the same Wi-Fi. When it is
  closed, Claude's changes wait in Review." Under them, on a phone or tablet: "Claude Code in the Claude app works
  through GitHub and doesn't need this." (G1)
- The connection is plain HTTP on the local network, with the token. The settings say "Only turn this on at home or on
  a network you trust."

## 16. Not in this spec

Pressure, tilt and barrel roll (section 10.4). Mac, Windows and Linux downloads made from an iPad (G25: iOS has no
Rust, and a release workflow that builds them belongs to the games' release work). Games in iCloud Drive (section
10.2). A Windows code-signing certificate. Creating the GitHub repository from inside the app (G6): it would need the
Administration permission, far more than sync needs, so the app opens GitHub's prefilled page once, in its own browser
sheet. A relay. Importing a hand edit of a generated file into a level. Creating GitHub repositories from inside the app. A
2D-only app or sale (the Owner, 21:33). The Microsoft Store and Steam (later, audit A11). Localisation (queued until the editors are feature
complete). A desktop job in a game's own release workflow (A14): games keep Tauri as a ship target, and whether their
template CI builds it again belongs to the games' release work, not to the editor app.

## 17. Risks

| Risk | Answer |
| --- | --- |
| Apple rejects the app under 2.5.2 | The code view, the game's own origin with no bridge, and review notes; budget one round |
