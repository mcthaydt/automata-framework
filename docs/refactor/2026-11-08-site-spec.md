1. A site that matches the approved Home mockup (`refactor/2026-11-06-redesign-mockups/site-home.html`) on every page:

5. The launch, in order: the Owner's accounts, the first release (0.1.0) on the new scope, Pixi 3D's public release
   with the repository opened the same day (plan audit A15), then the site. Nothing of AF is public before Pixi 3D is.

### 3.1 Avoiding conflicts with the open PRs

1. **Nothing renames before the stack merges.** Part C's PR is opened from `main` only when the merge thread reports
   the stack merged. Until then the codemod and its guard exist only on C's branch.
2. **Stragglers.** A PR that is still open after C merges (for example #379, #383, #404, #413, #422, #466 on `main`,
   or the skills PR #451 that waits for the first mirror push) is brought up to date in this order, never by a
   force-push:
   1. On the PR's branch, take main's codemod first, since the branch still has the old one that maps to `@automata`
      (`git checkout origin/main -- tooling/codemods/src/rename-scope.ts tooling/codemods/src/rename-scope-cli.ts`), run
      it (`node tooling/codemods/src/rename-scope-cli.ts`) and commit `chore: rename to @automataframework (codemod)`.
      Its lines now match `main`'s.
   2. Merge `origin/main` into the branch. Hunks that differed only by the name no longer conflict. On a
      `pnpm-lock.yaml` conflict, take main's (`git checkout --theirs pnpm-lock.yaml`); step 3 redoes it.
   3. Run the codemod again (catches names the branch added in the merge), `pnpm install`, `pnpm check`.
   The guard (`tooling/release/tests/unit/scope.test.ts`) fails `pnpm check` on any old name, so a straggler cannot
   merge with one.
3. **#431 (changesets "Version packages")** is closed, not merged: changesets opens a fresh one under the new names.
4. **The codemod is idempotent**: running it on renamed text changes nothing (a unit test proves it), so steps 1 and 3
   are safe to repeat.

## 4. The site (Part A)

### 4.1 One shell (I3, M6)

- One page width and gutter for every page: Home's (content and the header's logo start at the same x at every width;
  at 1440 px both at x = 120). A `PageShell.svelte` in `site/src/shared/components/` owns it; every route uses it.
- One type scale from the editor kit's tokens (`packages/editor/src/shared/kit/tokens/tokens.json`): titles bold
  (600), body 400. The "light display type" rule and its "glass" comment go.
- One code box, `CodeBlock.svelte`: highlighted (the docs' highlighter, `src/shared/utils/highlight.ts`), a 44 px copy
  icon button named "Copy code", no language header, long lines scroll inside the box (never cut). It keeps `lang` as
  any string the highlighter knows (the guides' markdown sets it) and a `label` shown as words above the box where a
  caller says where the code goes ("Copy this to your agent", "In your terminal"). `TerminalBox` and
  Home's command box become `CodeBlock` with `variant="command"` (one line, `$` prompt, ellipsis on overflow, the copy
  button copies the whole command).
- The current page's header link is marked by colour and an underline, not by weight, so nothing shifts (M6).
- `app.css` is split by concern under `src/shared/styles/` (tokens, base, layout, prose), each file under 600 lines;
  page-specific rules move into their components. `pnpm style` reads `site/src` only for plan comments today (a
  `--comments-only` root), so the 600-line rule is widened to every non-test file it reads, comments-only roots and
  `.css` included (plan audit A8; nothing else in those roots is over 600 lines).

### 4.2 Home's centrepiece (I1)

- The demo is the game's picture edge to edge (no title bar, no letterbox strips, no overlay boxes). One bar under it:
  "Emberwick", "A platformer made with Automata", and "Play it", the white secondary button as the mockup draws it (the
  hero's "Make a game" is the screen's one lime primary). Pressing it starts the game in the picture's place; the bar
  then shows "Emberwick", "Full screen" and "Stop" (on a phone the game is about 220 px tall, so Full screen is how it is
  played). While it starts the bar says "Starting Emberwick…"; if it fails, "Emberwick didn't start." and "Try again".
  Start over and Open in a new tab go (essentials); a refused full screen says "Full screen isn't available here."
- **The first press always counts** (plan audit A11). Hydration waits for the first paint or three seconds
  (`hydration.ts`), so a press before it would be lost. The inline start also begins on the first `pointerdown` or
  `keydown`, and a press on "Play it" before hydration marks `<html data-play-pressed>`; `DemoRunner` starts the game on
  mount when the mark is set. The visitor presses once.
- The command box is the `command` variant of 4.1: `npx @automata/tools create-game my-game` (Part C renames it).
- "Small files. Plain TypeScript." shows the code highlighted, labelled "What it draws" (kept: it says what the right
  side is; "Running" does not). `copy.md` records it.
- `Home.svelte` (553 lines) splits into one component per section in `src/features/home/`.

### 4.3 Pictures (I2, I4)

- One script, `site/scripts/take-pictures.ts`, takes every poster and every Editor page picture from the built site
  and the built try-it editor, with Playwright, at fixed sizes and a fixed time: a built demo has no tick or seed hook,
  so the script installs Playwright's `page.clock` before loading and advances it by a fixed number of milliseconds.
  Pictures of a game are shot from the game's canvas element, so no page markup is in the picture (anything the game
  draws itself, such as a pause button, is looked for by eye). The script writes JPEGs under today's names in
  `static/previews/` (`emberwick`, `double-jump`, `hot-reload`, `editor`, `editor-new`, `editor-phone`), which is what the
  pages load and what `encode-previews.ts` reads to write the WebP copies; there is no second folder. Two runs write the
  same bytes, or the log says why not. The pages take each picture's width and height from the script's list, not typed
  by hand. No hand-made screenshot is committed.
- The Editor page's pictures show the suite (15.1b) as the web keeps it (R7): Levels painting a room, the try-it
  templates, the suite on a phone. Each picture's caption names what is in it. The phone picture and "It works on a phone
  and a tablet too." wait until the try-it passes 4.4's phone check.
- The 2D examples' colours become DUEL: every hex colour in `examples/2d/**/*.ts` (tests excluded) is a
  `docs/art/palettes/duel.txt` entry (a repo-hygiene test fails otherwise; `examples/2d` has no unit project). Today none
  is (plan audit A7): twelve colours at 36 places in 15 files, `0xffffff` the most used. Each is replaced by the DUEL
  colour `nearestDuel` picks (`@automata/content/palette`, OKLab; it returns an index into `DUEL_RAMPS.flat()`, whose
  entries are `#rrggbb`); the failing test prints the pick. Views are presentation, not sim state (the examples' goldens
  are replays), so no parity hash moves; if one does, it is investigated (law 3). Home's code sample quotes
  `shapes-rects.ts` and `ShapesPreview.svelte` draws the same colours (a unit test compares them with the file).

## 5. Deploy (Part B)

- **5.1 Headers from one source.** `site/scripts/write-headers.ts` writes `build/_headers` from `securityHeaders()`
  for every path pattern it distinguishes (`/*`, `/demos/*`, `/editor/app/*`, `/examples/*`, `/playground/examples/*`,
  and the playground's own headers from `src/features/playground/headers.ts`). Cloudflare sends a request the headers of
  *every* rule that matches it and joins a header named twice with a comma (plan audit A2), so the path-independent
  headers (HSTS, `X-Content-Type-Options`, `Referrer-Policy`) are written only under `/*`, and no header but
  `Content-Security-Policy` reaches one path from two rules (two CSP headers are two policies, both enforced). `check:site`
  parses `_headers` with that rule and fails when any built file's headers differ from `securityHeaders(path)` plus
  the playground's. The same `check-deployed.ts` of 5.3 runs against `wrangler pages dev build` on the build machine,
  Cloudflare's own engine, before any account exists.
- **5.2 Upload.** `site.yml`'s upload runs `wrangler pages deploy site/build --project-name automataframework --branch
  main` (wrangler pinned in `site/package.json`), with `CLOUDFLARE_API_TOKEN` (the Owner's secret, replacing
  `SITE_DEPLOY_TOKEN` here, in `ci.yml`'s call and in the runbook's secrets table) and `CLOUDFLARE_ACCOUNT_ID` (a
  repository variable). The upload leaves out the build's `.br` and `.gz` copies (Cloudflare compresses on its own and
  would serve them as addresses). Without the token: "No host configured yet." and pass, as today.
- **5.3 Live check.** `site/scripts/check-deployed.ts <origin>` fetches Home, a demo, the try-it editor, `security.txt`
  and a missing address, and fails when a status or any header differs from `securityHeaders(path)`. `site.yml` runs it
  after the upload, on the deployment address `wrangler` prints and then on the domain. HSTS stays one day until the live check has passed for seven days; then a one-line PR raises it to
  a year (the runbook says so).
- **5.4 Launch check.** `check:launch` adds: the domain has an MX record (the mailbox exists);
  `@automataframework/tools` is on npmjs.org (after Part C the name is the new one; before it the check names
  `@automata/tools` and fails, as today); `@pixi/3d` is on npmjs.org (Pixi 3D is public; plan audit A15); and
  `REPOSITORY_PUBLIC` is `true` in `site.js` (the repository opened the same day). If the Owner gets PixiJS's written
  permission instead, the Pixi 3D question changes in a PR that quotes it.
- **5.5 Runbook.** "Launch the website" becomes: 1 register the domain and create hello@ (D2); 2 create the npm
  organisation `automataframework` and `NPM_TOKEN` (D1); 3 create the Cloudflare Pages project and attach
  `automataframework.com` to it as its custom domain (D3); 4 merge the rename; 5 approve the first release (0.1.0, from
  #440's `first-public-release.md`); 6 Pixi 3D is public: the AF 1.0 launch task swaps `vendor/pixi-3d/` for the npm
  release, the Owner opens the repository (the go-public checklist), and a PR sets `REPOSITORY_PUBLIC` to `true`; 7 add
  `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, last, since every push to `main` before steps 5 and 6 would fail
  `check:launch`; the next push deploys; 8 look at it on a phone and the iPad, and make a level in Try the editor; 9
  archive `automata-website` (D5).
