## 1. What this slice delivers

1. A site that matches the approved Home mockup (`refactor/2026-11-06-redesign-mockups/site-home.html`) on every page:
   one page shell, one type scale, one code box, slightly rounded corners (`--edge-sm/md/lg`, never a pill), DUEL
   pictures, YC-level polish to the taste-skill standard, and copy that passes the drunk grandma test.
2. A site that can deploy: a host, its headers from one source, a checked live origin, a runbook that starts at
   "register the domain".
3. Every package renamed to the `@automataframework` npm scope in one mechanical pass, after the open PRs merge, with
   a guard that keeps old names out and a recipe for any PR that lands later.
4. The launch, in order: the Owner's accounts, the first release (0.1.0) on the new scope, then the site.

### 3.1 Avoiding conflicts with the open PRs

1. **Nothing renames before the stack merges.** Part C's PR is opened from `main` only when the merge thread reports
   the stack merged. Until then the codemod and its guard exist only on C's branch.
2. **Stragglers.** A PR that is still open after C merges (for example #379, #383, #404, #413, #422, #466 on `main`,
   or the skills PR #451 that waits for the first mirror push) is brought up to date in this order, never by a
   force-push:
   1. On the PR's branch, run the codemod first (`node tooling/codemods/src/rename-scope-cli.ts`) and commit
      `chore: rename to @automataframework (codemod)`. Its lines now match `main`'s.
   2. Merge `origin/main` into the branch. Hunks that differed only by the name no longer conflict.
   3. Run the codemod again (catches names the branch added in the merge), `pnpm install`, `pnpm check`.
   The guard (`tooling/release/tests/unit/scope.test.ts`) fails `pnpm check` on any old name, so a straggler cannot
   merge with one.
3. **#431 (changesets "Version packages")** is closed, not merged: changesets opens a fresh one under the new names.
4. **The codemod is idempotent**: running it on renamed text changes nothing (a unit test proves it), so steps 1 and 3
   are safe to repeat.

## 4. The site (Part A)

### 4.1 One shell (I3, M6)

- One page width and gutter for every page: Home's (content and the header's logo start at the same x at every width;
  at 1440 px both at x = 120). A `PageShell.svelte` in `site/src/shared/components/` owns it; every route uses it.
- One type scale from the editor kit's tokens (`packages/editor/src/shared/kit/tokens/tokens.json`): titles bold
  (600), body 400. The "light display type" rule and its "glass" comment go.
- One code box, `CodeBlock.svelte`: highlighted (the docs' highlighter, `src/shared/utils/highlight.ts`), a 44 px copy
  icon button named "Copy code", no language header, long lines scroll inside the box (never cut). `TerminalBox` and
  Home's command box become `CodeBlock` with `variant="command"` (one line, `$` prompt, ellipsis on overflow, the copy
  button copies the whole command).
- The current page's header link is marked by colour and an underline, not by weight, so nothing shifts (M6).
- `app.css` is split by concern under `src/shared/styles/` (tokens, base, layout, prose), each file under 600 lines;
  page-specific rules move into their components. `pnpm style` (which already reads `.css` for plan comments) counts
  `.css` files under the same 600-line rule.

### 4.2 Home's centrepiece (I1)

- The demo is the game's picture edge to edge (no title bar, no letterbox strips, no overlay boxes). One bar under it:
  "Emberwick", "A platformer made with Automata", and a primary button "Play it". Pressing it starts the game in the
  same frame; the bar then shows "Emberwick" and a "Stop" button.
- The command box is the `command` variant of 4.1: `npx @automata/tools create-game my-game` (Part C renames it).
- "Small files. Plain TypeScript." shows the code highlighted, labelled "What it draws" (kept: it says what the right
  side is; "Running" does not). `copy.md` records it.
- `Home.svelte` (553 lines) splits into one component per section in `src/features/home/`.

### 4.3 Pictures (I2, I4)

- One script, `site/scripts/take-pictures.ts`, takes every poster and every Editor page picture from the built site
  and the built try-it editor, with Playwright, at fixed sizes, a fixed seed and a fixed tick count. Pictures of a game
  are shot from the game's canvas element, so no page control (the pause button) is in the picture. The script
  writes `static/previews/` and `static/editor-pictures/`, and `encode-previews.ts` encodes them. No hand-made
  screenshot is committed.
- The Editor page's pictures show the suite (15.1b): Levels painting a room, the try-it templates, the suite on a
  phone. Each picture's caption names what is in it.
- The 2D examples' colours become DUEL: every hex colour in `examples/2d/**/*.ts` is a `docs/art/palettes/duel.txt`
  entry (a repo-hygiene test fails otherwise; `examples/2d` has no unit project). `0x00cdf9`, `0x5ac54f` and `0xf5555d`
  are replaced by the DUEL entry `nearestDuel` picks (`@automata/content/palette`, OKLab); the failing test prints it. Views are presentation, not sim state, so no
  parity hash moves; if one does, it is investigated (law 3). Home's code sample quotes `shapes-rects.ts` and
  `ShapesPreview.svelte` draws the same colours (a unit test compares them with the file).

### 4.4 The other pages

- **Missing page (I5):** today `404.html` is adapter-static's empty fallback shell, which paints nothing until the
  deferred start gives up after `FALLBACK_MS`. It becomes a prerendered page: a `NotFound.svelte` component, rendered by
  a prerendered route `src/routes/not-found/+page.svelte` (marked `noindex`, left out of the sitemap) and by
  `+error.svelte` for a 404; the build copies `build/not-found/index.html` to `build/404.html` and the adapter's
  `fallback` option goes. Its words: "Page not found", "There is no page at this address. It may have moved.", "Go to
  the home page" (primary) and "Read the docs".
- **Editor page and try-it (I4, I7):** the copy step's source is the suite's build (as #476 left it); the page's words,
  `docs/guides/editor.md` and Privacy's sentence on what the try-it editor keeps in the browser are reread against the
  suite; `check:site` is rerun and the try-it build's measured size logged (its budgets cover the pages' own scripts, not the
  try-it build, which no page preloads). Under a coarse pointer
  every try-it control is at least 44 px at every size (layout test); a fine-pointer desktop keeps the kit's density.
  Templates appear only on the try-it page (the Owner's rule): no other page offers a template.
- **Reference and extensions (I8):** the index groups packages under "Core" and "Extensions"; one guide,
  `docs/guides/extensions.md` ("Extensions: add what your game needs"), in `docs/guides/index.md`; "How it works" no
  longer counts packages.
- **Start (I9):** the agent setup is a plain numbered list (no checkboxes, no counter). The preflight reads "Then read
  this game's README.md and the package types." (`create-game` writes a `README.md`, not an `AGENTS.md`). If #451 has
  merged, these are its lines, changed the same way.
- **Contact (I6):** `CONTACT_EMAIL` and `SECURITY_EMAIL` are `hello@automataframework.com`, in `site.js`,
  `security.txt` and `SECURITY.md`. The Gmail address leaves every tracked file outside the history. The launch still
  waits for the mailbox (5.4).
- **Words (M5):** `llms.txt`'s editor line says what the guide is ("How to open the editors on your game"); `llms-full.txt`
  is "Every guide and API page in one file"; doc comments render backticks as code, not raw text.

### 4.5 Tests and code (I10, M1, M2, M4, M7)

- `site/package.json` gets `"imports": { "#src/*": "./src/*" }`; every site test imports site code as `#src/…`.
  `pnpm style`'s relative-chain rule covers `site/tests/`. Site tests import other packages only through their public
  entries (`@automata/tools/…` exports), never `packages/*/src`.
- The plan-citation check (2D build audit L1) also matches "(D8)", "(PLAY-D6)", "spec F-4", "QB-D3" and "§"; the 63
  lines are reworded to say why.
- Unused code goes: `virtual:framework/packages`, `src/shared/framework/packages.ts`, `apiVersions`/`latestApiVersion`
  (one version), `DemoRunner`'s `aspect` prop. `knip` covers `site/`.
- Stale comments go: `Footer.svelte`'s D8 note; `security-headers.ts`'s HSTS note names the live check of 5.3.
- The demo frame drops `sandbox` (first-party, same origin, where `allow-scripts allow-same-origin` protects nothing);
  a comment says so.

## 5. Deploy (Part B)

- **5.1 Headers from one source.** `site/scripts/write-headers.ts` writes `build/_headers` from `securityHeaders()`
  for every path pattern it distinguishes (`/*`, `/demos/*`, `/editor/app/*`, `/examples/*`, `/playground/examples/*`,
  and the playground's own headers from `src/features/playground/headers.ts`). `check:site` parses `_headers` and fails
  when any built page's expected headers differ from `securityHeaders(path)`.
- **5.2 Upload.** `site.yml`'s upload runs `wrangler pages deploy site/build --project-name automataframework --branch
  main` (wrangler pinned in `site/package.json`), with `CLOUDFLARE_API_TOKEN` (the Owner's secret, replacing
  `SITE_DEPLOY_TOKEN`) and `CLOUDFLARE_ACCOUNT_ID` (a repository variable). Without the token: "No host configured
  yet." and pass, as today.
- **5.3 Live check.** `site/scripts/check-deployed.ts <origin>` fetches Home, a demo, the try-it editor, `security.txt`
  and a missing address, and fails when a status or any header differs from `securityHeaders(path)`. `site.yml` runs it
  after the upload. HSTS stays one day until the live check has passed for seven days; then a one-line PR raises it to
  a year (the runbook says so).
- **5.4 Launch check.** `check:launch` adds: the domain has an MX record (the mailbox exists), and
  `@automataframework/tools` is on npmjs.org (after Part C the name is the new one; before it the check names
  `@automata/tools` and fails, as today).
- **5.5 Runbook.** "Launch the website" becomes: 1 register the domain and create hello@ (D2); 2 create the npm
  organisation `automataframework` and `NPM_TOKEN` (D1); 3 create the Cloudflare Pages project, add
  `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (D3); 4 merge the rename; 5 approve the first release; 6 the
  deploy runs from `main`; 7 look at it on a phone and the iPad; 8 archive `automata-website` (D5).
