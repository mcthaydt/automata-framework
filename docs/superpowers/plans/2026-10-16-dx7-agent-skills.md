## Decisions (made in this lane, from the spec and the repo's patterns)

- **D1. The hook script is Node, not shell.** Spec §3.7 names `scripts/check.sh`. The hook reads the event JSON from stdin (`tool_input.file_path`, `stop_hook_active`); a shell script would need `jq`, which a game machine may not have, and would not run on Windows without bash. Every Automata game has Node, so the hooks run `node "${CLAUDE_PLUGIN_ROOT}/scripts/check.mjs" post-edit|stop`. Same behavior, one file, testable by spawning it.
- **D2. Where the hook finds `automata`.** `node_modules/.bin/automata` from `${CLAUDE_PROJECT_DIR}` upwards (as DX.6 finds a game's tools). Not found: if the project's `package.json` depends on an `@mcthaydt/automata-*` package, the hook blocks with "add `@mcthaydt/automata-cli` as a dev dependency" (a missing checker is never a pass); otherwise the project is not an Automata game and the hook exits 0 silently, so a user-scope install doesn't block unrelated repos.
- **D3. `Stop` blocks once per stop.** When the event has `stop_hook_active: true` (Claude is already continuing because of this hook), the hook exits 0. Without that, a finding the agent cannot fix loops forever. `PostToolUse` checks every sim edit, so a sim finding still reaches the agent on each edit.
- **D4. Feedback text.** Exit 0 says nothing. On `automata check` exit 1 (findings) or 2 (tool error), the hook exits 2 with one line saying what failed and the check's `--json` report on stderr (§3.7 "Feedback"); if the check printed no JSON (it crashed), stderr carries its output tail.
- **D5. Two marketplaces, one plugin.** AF's root `.claude-plugin/marketplace.json` is named `automata-framework` (collaborators: `/plugin install automata@automata-framework`); the public mirror's is `automata-skills` (DX.11 writes it). Both list `{ "name": "automata", "source": "./agents/automata" }`-style entries to the same files.
- **D6. Plugin metadata and version.** `claude plugin validate --strict` (2.1.301) fails without `version`, `description` and `author`, so `plugin.json` carries them (spec §3.7 said `name` only). `version` is the API version stated in `reference/api.md`, and a test keeps them equal: Claude Code refreshes an installed plugin when its version changes, and the API reference is "exactly this version".
- **D7. `reference/api.md` is committed and checked.** DX.4 writes `tooling/api-index/dist/api.md` (not committed). A plugin installed from git needs the file, so the skill carries a committed copy; `pnpm agent-skills` fails when it differs from the generated one (run after `pnpm build && pnpm api-index`) and `pnpm agent-skills --write` copies it. It runs in `ci.yml`'s checks job and `ci:local` right after `pnpm api-index`.
- **D8. `claude plugin validate` in CI through `pnpm dlx`.** `pnpm plugin:validate` runs `pnpm dlx @anthropic-ai/claude-code@2.1.301 plugin validate --strict` on `agents/automata` and on the repo root (the marketplace). Not a devDependency: it pulls a platform binary into every install. The pin gets a `docs/versions.md` row.
- **D9. The worked example lives in the skill and is checked from `tooling/agent-skills`.** `skills/automata-feature/example/src/sim/` holds the double-jump component, command, system, plugin and golden test, laid out as a game's `src/sim/`. `tooling/agent-skills` typechecks it (`tsconfig` include and `paths` to `packages/sim`), runs its test (vitest include and aliases), and `pnpm boundaries` checks it. The view step stays prose until DX.2b's `rect`/`sprite` views exist; DX.3 or DX.5 adds view code.
- **D10. `examples/base-2d` gets `@mcthaydt/automata-cli` as a dev dependency**, so the reference game has its own `automata` bin, as DX.5's generated games will. The install test runs the installed hook against it.
- **D11. Rules documented from the code.** A test collects every rule id the checks can emit (check-boundaries' `Rule` union and the `rule:` literals in `packages/cli/src/check/*.ts`) and fails when `automata-verify` doesn't document one.
- **D12. Install tests are scripted but not in `pnpm check`.** `pnpm --filter @mcthaydt/agent-skills test:install` needs the `claude` CLI and the npm registry, which the hosted unit job lacks. It uses a throwaway `CLAUDE_CONFIG_DIR` and `HOME`, so it never touches the user's Claude settings. Its output is the install log recorded in spec §3.7 "As built".
- **D13. `npx skills add` pinned to `skills@1.7.0`** (2026-09-17; 1.7.1 and 1.7.2 are under two weeks old) and tested for the agents it installs into: Claude Code (`.claude/skills/`) and Codex and Cursor (`.agents/skills/`). The test checks the files land byte-identical to the source; it cannot start Codex or Cursor, and the log says so.
- **D14. Skill-tree identity is a library now, wired later.** `diffSkillTrees(a, b)` (paths whose bytes differ, or exist on one side only) is what DX.5 (copies into generated games) and DX.11 (the public mirror) call. DX.7 tests it and uses it on the `npx skills add` copies.
