## Planning notes (read before Task 1)

These are choices the spec leaves open or file names the repo's rules force. Each is also listed in the report to the Owner; none changes a contract.

1. **Bench file name.** §7 names `loop/frame-loop.bench.ts`, but `pnpm style` rejects the unknown role `bench`. Use `loop/frame-loop.bench.test.ts`, as `packages/sim` does (`xxhash64.bench.test.ts`), kept out of the gate by a `bench` project.
2. **Page layers file name.** The loader's progress and slow line are reactive props, which need Svelte runes, so §3.1's `boot/page-layers.ts` is `boot/page-layers.svelte.ts` (the style checker accepts the `.svelte.ts` marker).
3. **Task order.** `ScreenDef.enter` requires `RuntimeServices`, which names the `Settings`, `AppLoop` and `Renderer` tags, so settings, the renderer interface and the app loop come before Flow.
4. **Error classes** live in `boot/boot-error.ts` (§3.1). The loading tasks add `LoadStalled` and `AssetLoadFailed` there first; Task 9 adds `RendererUnavailable`; Task 15 completes the union. Every error class follows `packages/host/src/errors.ts`: a typed base (`const XBase: TaggedErrorClass<'X', Fields> = Data.TaggedError('X')`), then `export class X extends XBase {}`, because the repo builds with `isolatedDeclarations`.
5. **`Assets.load(screen, onProgress?)`.** §3.4 gives `load(screen)` and "shared progress for every waiter"; the optional second argument is how a waiter hears it.
6. **`readBlob` only.** FloorFifty's `fetch-progress.ts` has `readJson` and `readBlob`; the runtime only fetches files, so only `readBlob` is ported and the JSON cases are rewritten for bytes.
7. **Settings service shape** (§3.7 names the `Settings` tag but not its fields): `interface Settings { readonly key: string | undefined; readonly store: SettingsStore<unknown> | undefined }`; `settingsStore(def)` returns that store when `def.key` matches, and dies with a defect otherwise (a bug in the game).
8. **Flow internals.** `makeFlow` returns `{ flow, start, reportFailure }`: `start` enters the entry screen (spec §2's `Flow.start`), `reportFailure` is how the app loop's fault reaches the `ScreenFailed` panel. `dispatch` matches its event against the screen the queue will be on (the last queued target, else `current`), so its boolean answer is immediate (Q3).
9. **`manifest-field`** is thrown by `resolved.manifest(config)`, the first point at which an untyped contribution can be seen (ship and the Vite config call it at build time).
10. **Seams** (§3.3 leaves them untyped): `{ fetch?: typeof fetch; frames?: FrameSource; fonts?: Pick<FontFaceSet, 'load'>; sdkEnv?: () => NonNullable<HostingSeams['env']>; document?: Document }`. `sdkEnv` is a function so each boot attempt gets an env (Try again makes a new SDK session).
11. **`RuntimeHandle.shutdown`.** §3.3 types it as a `Promise<void>` property, which cannot start a shutdown. This plan uses `shutdown(): Promise<void>` and flags it for the Owner; Task 17 is the only place that depends on it.
12. **Dev logging** of an unmatched event (Q3) reads `import.meta.env?.DEV === true`, typed by a small `src/env.d.ts`.
