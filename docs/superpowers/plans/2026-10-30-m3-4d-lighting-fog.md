## Why

Static scenery needs light that reads in the angled view without real-time lights per fragment, characters need to darken and brighten as they walk past lamps, and the far side of a room closes into fog (spec §4.2: "every authored room closes its far side with a wall or fog"). M3.4a's example shows the gap: with only a sky-and-ground fill, the props read dark. M3.5d's figure view and M3.7b's rooms consume this task's `SceneLight` and `characterTint`.

## Decisions (agent defaults, for the Owner's veto)

1. **Content shape.** Kind `scene-lighting`, a collection under `content/lighting/` (one TOML file per room), `sim: false` (presentation, law 1). `SceneLighting { ambient, ambientColor, lamps, boxes, planes, fog? }`: `ambient` 0 to 1 (spec), `ambientColor` (default white), `lamps: Lamp[]` (`id`, `x`, `y`, `z`, `color`, `strength` default 1, `range` > 0, `level` default 1, the level before the sim says otherwise), occluder `boxes` (`x`, `y` the base, `z`, `width`, `height`, `depth`, optional `id`) and `planes` (centre, `normal`, `width`, `height`; one-sided for contact darkening, both sides block light), and an optional `fog { near, far, color }`. Colours are 0xRRGGBB integers (TOML hex). Lamp ids are unique within a file: a duplicate is a compile error at its `id`'s line and column. Boxes and planes are in the lighting file because there is no room content kind yet (2026-10-16 §4.4: "occlusion takes boxes and planes from the room content"); M3.7 or `sectors` (M6) can feed them from rooms later.
2. **The kind is registered by `render3dExtension`** with `defineContentSchema`, as `figures` does, in `scene-lighting.content.ts`. (Review fix, 2026-10-30: the first version wrote the registration out by hand with a type-only import, on the guess that the content package's root entry would carry its Node-only compiler into every 3D game's browser bundle. Measured instead: a Vite browser build of `defineContentSchema` alone from the root entry tree-shakes to 1,091 bytes, with no `node:` import and no compiler code; Vite only warns that the compiler's `node:` modules were externalized while it resolves them. So the guess was wrong and the helper is used.)
3. **The light model.** A vertex's colour is `(ambient × ambientColor + Σ level × strength × max(0, N·L) × (1 − d/range)² × lampColor) × contact`, clamped at 1.6 (the source's ceiling), multiplying the material's base colour (`vertexColors`). Occluded lamps add nothing (the sample is nudged 3 cm off its surface; a box whose `id` the mesh lists in `ignore` never shadows it). Static meshes use `FlatMaterial`, so only this light reaches them (no View3D lights).
4. **Baking and rebaking.** `SceneLight.bake(mesh)` reads the mesh's own position, rotation and scale as its world placement (a static mesh sits on the view's root), swaps in a dynamic copy of its geometry with vertex colours (the source geometry is not destroyed; it may be shared) and turns `vertexColors` on. Each lamp's light per vertex is computed once at bake (lamps do not move); a level change recomputes the colours of the meshes that lamp reaches and no others, and uploads only when a colour changed. `rebakes` counts meshes recomputed.
5. **The sim seam for lamp changes.** `Pixi3dOptions.lamps` names a component whose entities switch lamps: `{ lamp: string, level: f32 }`. The renderer reads it from the render deltas (added and changed set the level; removed and resync return a lamp to its content `level`) and calls `setLevels`. No new sim API: a game spawns the entity and sets its `level` from a system, which is the "sim event".
6. **Characters and static boxes.** `characterTint(position, normal, lighting, levels)` is ambient plus N·L of the lamps in range at the position (no normal: the light from every direction, the source's `lightAt`), with the same occlusion, as `[r, g, b]`; `SceneLight.tint(x, y, z, normal?, out?)` is the same with the colours decoded once and an output array, so a frame allocates nothing. `box(size, { color, lit: 'moving' })` uses it per frame as `FlatMaterial.baseColor = color × tint` (multiplied in linear light, back to sRGB) when the renderer has lighting, with no normal (a box is not a figure); the figure view (M3.5d) passes normals per part. **Deviation from spec §4.3 / M3R-D4, for the Owner's veto:** the spec says the tint goes on `@pixi/3d`'s *lit* material; this uses an unlit `FlatMaterial`, because a lit (Phong or PBR) material would also take the View3D's own lights and environment, so a character would be lit twice and would not match the baked scenery beside it, which takes only this light. If the Owner wants the lit material, the scene must carry no View3D lights or environment and the tint goes on its base colour. `box(size, { color, lit: 'static' })` is scenery: subdivided every 25 cm (whether or not the renderer has lighting) so vertex light has vertices to land on, baked once at its first pose and released when destroyed; it has no `ignore` (a mesh that needs one is baked with `SceneLight.bake(mesh, { ignore })`).
9. **Colours in linear light.** Lamp and ambient colours are authored in sRGB like every `@pixi/3d` colour and decoded to linear light before they multiply a surface, since the shader works in linear light (the source multiplied its sRGB values directly).
10. **Contact darkening is the source's rules.** Upright planes take the source's wall rule, its strength by the surface's own facing (0.38 floor or top, 0.3 upright, 0.15 underside, reach `exp(-d/0.28)` to 0.9 m); a floor plane darkens upright surfaces above it by `0.28 · exp(-d/0.35)` and a ceiling plane those below it by `0.3 · exp(-d/0.35)` (the source's wall-foot and drawn-ceiling terms); box feet as the source's furniture. (The first version chose the strength by the surface's angle to the plane, a reinterpretation; the review asked for the faithful rule.)
11. **Reading geometry.** The bake reads tightly packed `float32x3` positions and `float32x3` or `snorm16x4` normals, and refuses an interleaved geometry naming the attribute. The baked copy keeps positions, normals, UVs and indices; tangents, joints and weights and a source's own `COLOR_0` are dropped. A lamp level from the sim below 0 is 0, and a non-finite one is ignored. `Pixi3dOptions.fog` is checked by the content's fog schema (`near < far`, a valid colour) and throws otherwise.
7. **Fog.** `Pixi3dOptions.fog` (spec §4.1), or else `lighting.fog`, sets `View3D.fog` to `{ type: 'linear', near, far, color }`. No fog when neither is set. No mist (S7 has not measured it).
8. **`scene` gets the light.** `scene(view, stage, light)`: the third argument is the `SceneLight` (undefined without `lighting`), so a game bakes its static scenery there; entity view factories get it as a fourth argument. Both are additive.

## Findings and notes for the Owner

- **Fog colour in the beta (0.1.0-beta.2).** A fully fogged pixel draws the fog colour's *linear* value: `0x3e3546` shows as about `0x0c0910`, as if the fog mix ran after the display encode, though the fog bit's own comment says it runs before it. The parity test pins today's behaviour (pixels move toward the drawn colour) and names it. Until the beta changes, authored fog reads darker than its colour; worth a report to the Pixi 3D team.
- **Record only (review items 9, 10, 12).** A static box has no `ignore` (decision 6). Static boxes are subdivided even with no lighting (decision 6, and the doc comment). `packages/editor-3d` also exports a `lampSchema` (`format/blockout.schema.ts`, The Last Light's blockout lamp with `on`); no row says which task turns blockout lamps into `scene-lighting` lamps. The candidates are M6.4b ("sector shade and wall runs feed M3.4's light and occlusion") and M6.11 (the blockout pipeline's generate stage); for the Owner to assign.
- **Mist** is not built: S7 has not measured it (spec §4.3).
