## Scope

  `sawHide`) and effects (`setMode`, `goTo`, `flee`, `noise`, `set`, `emit`, `call`, `followThrough`, `ambush`);

  waiting facts), the rule ticks (`every`, halt on a catch or a cutscene) and hearing when a noise is made;

- `reserveNodes` and `reachable`, taken over from nav (N-D3);
- a one-off converter for the four scenes, a four-engine golden, and SY-a.

- **Per step** (§5): input commands; then in `gameplay` the `systems.rules` system (crossings first when the def uses
  portals, then rules in order, stopping on a halt) and the `systems.agents` system (agents in id order: transitions,
  movement, pending appearances); then in `cleanup` sectors' membership and the noises' ageing.
- **Halt.** A rule effect that catches the player or starts a cutscene ends the systems' step: later rules and the
  agents wait for the next step, as in the source.
- **Hearing.** `hear` puts the noise in `systems-noises`, emits `systems.noise`, and runs the hearing rules and the
  agents' hearing transitions at once, on the step the noise is made. A `footfall` is never heard (`UNHEARD`).
- **Loading.** The first step after `systems-scene` is set spawns one entity per agent (at `place` from a restore, else
  its first routine node, else the origin) and zeroes every rule clock. A restore brings the resources back, so the
  entities and their state match.
- **Failure policy** (§6): an unknown hook, mode, node or agent, a probe a world rule cannot ask, and a sense a probe
  needs but the agent lacks are content errors at compile time, each with file and line. A scene with no nav graph or
  sector map fails to load with the scene's name; nothing falls back to an empty graph.

## Decisions for the Owner's veto

- **SY-D1:** an agent is an entity with sectors' `InSector` (its plan position, as N-D2) and a `systems.agent`
  component holding its index; its mode name, path, goal, timers and pending appearance live in `systems-state`,
  because components hold only numbers.
- **SY-D2:** noises from other extensions reach `systems` through `hear(ctx, noise)`, which a game passes to puzzle's
  new optional `noise` option. A system cannot read another's events on the same step (P6-D2 as built), and sound is
  heard when it is made. Puzzle does not import `systems`.
- **SY-D3:** `SystemsEnv` is data the game writes each step: light discs (`x`, `z`, `radius`), warm things (`x`, `z`,
  `kind`) and whether the player is moving. The source's `lit(w, p)` becomes "the first disc, in order, that covers
  `p`". A game with other light shapes writes the discs it needs.
- **SY-D4:** hooks, derived facts and refused steps are functions given to `createSystemsPlugin`, run inside the
  systems' own steps, as puzzle's calls (P6-D2 as built). Law 1 holds: only sim code changes state.
- **SY-D5:** `fact` probes and `set` effects use puzzle's facts (`puzzle-state` and the game's mapped facts), so a fact
  has one owner. `systems` depends on `puzzle`, which already owns `Value` (§3).
- **SY-D6:** a crossing is read from the player's `InSector.sector` against last step's, so `crossed` holds on the step
  after the player's move (sectors decides membership in `cleanup`). The source read it on the same step. The pursuit
  tests pin the one-step offset.
- **SY-D7:** hiding is the `systems.hide { spot, at }` and `systems.unhide` commands. Moving brings the player out
  (from `SystemsEnv`), as in the source. `withHiding` stays the game's.
- **SY-D8:** `systems` moves its agents itself with nav's `route` and `clear`, rather than through nav's `walk-to`
  command (commands are input from outside the sim). Sight is walls only (`segmentBlocked`), as the source's
  `wallsOnly` default; movement uses nav's `blockedBy` or the game's `blocked` option.
- **SY-D9:** the `systems-patrol` example moves to a follow-up row after M6.4b, as M6.5's example does.
- **SY-D10:** `systems` is private, like `sectors`, `nav` and `puzzle`.
