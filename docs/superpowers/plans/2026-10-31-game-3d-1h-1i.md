## Scope

### Part 1 (1h, core, if A): the game half of M4.12

1. `packages/game` play screen: mounts `CameraDragSurface` over `Input.drag` when the profile binds `camera-drag`, and
   passes `Input.touchStick` to `TouchControls`'s stick, as M4 §16.4 specifies (the spec already holds the flow; no

2. A binding for analog commands in `packages/game`'s input API, e.g. `analog(Move, { stick: 'left' })` and

   or `turnUnitsFromPixels(cameraDrag(), speed, invert)` plus the right stick's turn at 180°/s, clamped to ±8,192
   (G3-F5). **New public API, for the Owner's veto;** written into M4 spec §16 as an addendum first, with a patch
   changeset, `api-report --update`, `agent-skills --write`.
3. Tests first in `packages/game` (DOM: the surface mounts only when bound, the stick drives `stick('left')`; unit:
   the analog payloads, the clamp, a `NaN` dropped), then Emberwick's touch e2e unchanged.

### Part 2 (1h, base-3d): §14's mapping

- Keys as §14.2 (F lock, L/Left Shift shield, J or the left button on the scene attack, Space/K action, R item, 1/2/3

  (Attack, Action, Shield, Lock, Item) in the `end` group, all `required`, the stick, the drag; while locked, a drag of
  40 px or a right-stick flick past 0.7 cycles (`lockInput` grows those sources); Q/E stay turn or cycle.
- `rotate: false` views and the lock ignore `camera-turn` (sim already); the settings' camera speed and invert apply
  (G3-aa).
- Cases: G3-v (each `hostReserved` variant at 844×390 and 780×270: the stick zone and five buttons full size,
  `checkLayout`, a scene point between them reaches the drag surface), G3-aa (0.5 speed doubles the units of the same
  drag; invert negates; Hold releases on release), G3-F5 (`NaN` never reaches the sim, ±8,192 clamp, no turn while
  locked or in `rotate: false`), the remap in the DOM, the e2e journey's input halves (touch-only, keyboard-only,
  pad-only reach the kiln's first door).

### Part 3 (1i): the level file

- `src/content/levels/kiln.af-sector.json`: R1 Furnace Mouth, R2 Bellows Gallery with its niche, R3 Hearth Chamber
  (§0.2), authored in ED3D where it can (the agent drives ED3D's model through its codec, not its UI: a gap logged);
  sectors with `view` ids, `occlude` walls, door portals, the slag channel as a pit sector, and the pieces as entities
  (§10's defs, part 1 of 1f).
- **Reading it:** a content-time converter (the game's Vite content step, Node side) from the file to `AreaSource`:
  each sector a room box (axis-aligned rectangles only in 1.0: a non-rectangular sector is a load error naming the
  sector, an editor gap if the content wants one), each wall edge that is not a portal a wall box `WALL_THICK` thick,
  door openings left open (the `door` entity fills them), pit sectors as pits, `spawn` and `area-exit` entities as the
  area's spawn and exits. The game consumes ED3D's schema, never a copy: **request to the ED3D lane** for a
  `./format` subpath export of `editor-3d` (the schema and codec only, no UI), or, if declined, the converter
  validates with `@mcthaydt/automata-sector-format` (core) plus the envelope fields it reads.
- `first-slice.ts` stays for the golden replay (its route and hashes stand); the kiln file becomes the game's second
  area through `compileWorld`, entered from the first slice's kiln (an `area-exit`), so New game reaches it.
- Cases: the file loads and compiles; G3-p (`checkWorld`) and G3-q (`solveWorld`, §0.2's path) pass over it; a bad file
  fails the build naming its file and JSON path (G3-F2's "file"); `EDITOR-GAPS.md` created with each gap (id, editor,
  what, workaround).
- Goldens: the route's world gains the second area, so its content hash moves (explained); every other assertion
  stands.

Notes for part 1, read on `main` `de753c9` (merged into this branch):
- `packages/game/src/input/keys.ts`: `keys(command, bindings, options)` builds an `InputMap` (`command`, `touch`,
  `touchButtons`, `touchMode`, `profile`, `labels`, `toCommand(held, tick)`, `attach(window) → InputSource`);
  `inputs(...maps)` (inputs.ts) merges maps. Payloads are merged over an idle payload and parsed by the command's
  schema; one action per distinct payload; the profile goes through runtime's `inputProfileSchema`. Analog values do
  not fit "one action per payload", so `analog()` is a separate `InputMap` kind whose `attach` reads
  `Input.stick(side, padAxes)` and `Input.cameraDrag()` each tick and whose profile binds `camera-drag` (that binding
  is what turns the drag on, input-profile.schema.ts).
- The play screen (packages/game/src/screens/PlayScreen.svelte) must mount `CameraDragSurface` (ui) with a
  `CameraDragTracker` (runtime) over `Input.drag` when the profile binds `camera-drag`, and pass `Input.touchStick`
  to `TouchControls`' stick (M4 §16.4 "Boot"; §16.3.7 for the surface's props and pointer pass-through).
- Turn units: `turnUnitsFromPixels(dx, degPerPixel, invert)` and the core `camera` settings (speed, invert) are in
  runtime (`input/analog/`); the right stick turns at 180°/s (DESIGN §14.3: 546 units a tick at 60 Hz), clamped to
  `MAX_TURN_UNITS_PER_STEP` (8,192).
